# Стенд ручных проверок в живом приложении

Четыре скрипта, которыми проверяется то, что не ловится тестами: раскладка,
цвета, поведение при нажатии. Каждый из них написан не сразу — каждый оплачен
отладкой, и правила ниже выведены из настоящих провалов, а не придуманы.

```powershell
powershell -File bench\ui\shot.ps1  C:\путь\снимок.png
powershell -File bench\ui\keys.ps1  "^p" "имя файла" "{ENTER}"
powershell -File bench\ui\keys.ps1  -At 314,83 "{ENTER}"
powershell -File bench\ui\keys.ps1  -NoClick "{ESC}"
powershell -File bench\ui\keys.ps1  -Chord "ctrl+shift+p"
powershell -File bench\ui\click.ps1 314 83
powershell -File bench\ui\click.ps1 592 262 ctrl
powershell -File bench\ui\click.ps1 592 262 right
powershell -File bench\ui\hover.ps1 200 83
```

Координаты — от левого верхнего угла окна, в той же системе, в которой снят
снимок `shot.ps1`. Приложение должно быть уже запущено.

## Почему они устроены именно так

**Снимок — через `PrintWindow` с флагом `PW_RENDERFULLCONTENT` (`0x2`).**
Передний план из фонового процесса дают не всегда, а `PrintWindow` работает
и с неактивным окном. Без флага содержимое WebView2 в снимок не попадает —
получится пустой прямоугольник.

**Передний план забирается через `AttachThreadInput`, и результат
проверяется.** `SetForegroundWindow` из фонового процесса Windows блокирует;
без проверки нажатия уходят в чужое окно — однажды ушли прямо в проводник.

**Переднего плана мало для клавиатуры.** WebView2 держит содержимое
в дочернем окне, и пока щелчка внутрь не было, фокус остаётся на рамке:
нажатия приходят в приложение и не доходят до вебвью. Поэтому `keys.ps1`
сначала щёлкает в рабочую область.

**Перед щелчком окно прибивается к началу экрана** (`SetWindowPos`). Окно
между вызовами переезжает, и координаты, посчитанные от прошлого положения,
попадают мимо на сотни пикселей — при этом скрипт бодро отчитывается
об успехе.

**После перемещения окна первый щелчок приходит с прежними координатами.**
WebView2 держит содержимое в дочернем окне и о новом положении узнаёт
не мгновенно. Щелчок, посланный слишком рано, доезжает до вебвью
с координатами от прошлого места — и всё, что открывается по щелчку,
появляется ровно на столько же в стороне. Первый же прогон задачи 32
выглядел как ошибка в расчёте положения меню: окно стояло в (52,150),
и меню вышло на 52 левее и на 150 выше точки. Поэтому `click.ps1` двигает
окно, только если оно и правда не на месте, и после перемещения ждёт дольше.

**Окон ZeroNote может быть два** — установленное и собранное для отладки.
Первое попавшееся брать нельзя: нажатия уйдут в чужое окно, а понять это
можно будет только по снимку. Скрипты требуют `ZERONOTE_PID`, если находят
больше одного:

```powershell
$env:ZERONOTE_PID = "4200"
```

**`SendKeys` считает служебными `+ ^ % ~ ( ) { } [ ]`.** Их надо оборачивать
в фигурные скобки, иначе регулярное выражение доедет искалеченным.

**`-At` задаётся только по имени.** Пока у нажатий не было объявлено позиции,
`-At` забирал нулевую: вызов `keys.ps1 "^w"` принимал нажатие за координаты,
ругался на разбор числа — и всё равно печатал «отправлено». Тот же вид,
что у прошедшей проверки.

**Сочетания шлются через `-Chord`, а не через `SendKeys`.** `SendKeys`
отправляет нажатие без скан-кода, и это ломает ровно то, ради чего стенд
заводился. Скан-код — то, из чего Chromium делает `event.code`, а вся наша
раскладка построена на нём (`keymap/binding.ts`). Без него `Alt+Shift+0`
приезжает в приложение как `)` и не совпадает ни с одним сочетанием,
а `Ctrl+C` не превращается в команду копирования вовсе.

Отсюда `-Chord`: он берёт сочетание в том же виде, в каком оно пишется
в `keymap.toml`, и добывает скан-код через `MapVirtualKey`.

```powershell
powershell -File bench\ui\keys.ps1 -At "500,145" -Chord "home,shift+end,ctrl+c"
```

Полтора дня две проверки подряд выглядели как дефекты приложения: сначала
«`Ctrl+C` не копирует», потом «`Alt+Shift+0` не разворачивает». Оба раза
виноват был стенд. Текст и одиночные клавиши по-прежнему через `SendKeys` —
там скан-код не нужен.

**Первое действие после смены переднего плана иногда пропадает.** Каждый
вызов `keys.ps1` и `click.ps1` — новый процесс, и он заново забирает передний
план. Первое нажатие или щелчок при этом доезжает не всегда: палитра остаётся
открытой с набранным запросом, кнопка не нажимается. Повторный такой же вызов
срабатывает. Снимок при этом выглядит так, будто приложение ничего не сделало,
— и на этом легко начать чинить исправную команду. Не сработало один раз —
повторить, и только потом искать причину в приложении.

**Системное окно в снимок приложения не попадает.** `shot.ps1` снимает окно
ZeroNote через `PrintWindow`, а `message()` и `ask()` из `plugin-dialog` —
это отдельные окна Windows. На снимке их нет, зато видно кнопку, застрявшую
в состоянии «Проверяю…», — и это читается как зависание. Такие проверки
снимаются целиком с экрана:

```powershell
Add-Type -AssemblyName System.Windows.Forms, System.Drawing
$b = [System.Windows.Forms.Screen]::PrimaryScreen.Bounds
$bmp = New-Object System.Drawing.Bitmap($b.Width, $b.Height)
[System.Drawing.Graphics]::FromImage($bmp).CopyFromScreen($b.Location, [System.Drawing.Point]::Empty, $b.Size)
$bmp.Save("экран.png")
```

## Главное правило

Целиться надо по проверке, а не по вере: щёлкнуть, снять экран, убедиться,
что попал. И если что-то не сработало — сначала проверить стенд на команде,
которая точно работала раньше (`Ctrl+N`), а уже потом чинить приложение.
Трижды за этап 2 виноват оказывался стенд.
