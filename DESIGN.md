# ZeroNote — проектный документ

Живой документ. Обновляется в том же коммите, что и изменение, которое он описывает.

---

## 1. Что это

Редактор, который совмещает две вещи, сегодня живущие раздельно:

1. Быстрый универсальный текстовый редактор уровня Notepad++ — мгновенный старт,
   любые файлы, любые кодировки, поиск с регулярными выражениями.
2. Работа с хранилищами Obsidian: хранилище открывается как папка/проект,
   несколько проектов одновременно в одном окне (модель VS Code / PlatformIO).

Целевой пользователь — разработчик, у которого заметки и код лежат рядом.

### Границы первого круга

В работе: только Windows 10/11, только локальная файловая система.

Явно вне области — не реализовывать и не закладывать: синхронизация и облако,
Linux, Android, шифрованные контейнеры, менеджер паролей, плагинный API, макросы,
пользовательские синтаксисы (UDL), LSP и автодополнение, сравнение файлов,
FTP/SFTP, совместное редактирование.

Нарушать нельзя никогда. Каждый закрыт автоматическими тестами — ссылки

Никакого автоформатирования и нормализации без явной команды. | `roundtrip::every_fixture_survives_open_and_save`, `roundtrip::editing_preserves_encoding_and_line_endings`, `document::tests::*` |

## 3. Модель данных

- **`Workspace`** — одно окно. Список корней и список открытых буферов.
  Сериализуется целиком как сессия.
- **`Root`** — корневая папка, добавленная в рабочее пространство. Имеет признак
  `is_vault` (определяется по наличию `.obsidian`), собственные правила
  игнорирования и собственный индекс.
- **`Buffer`** — открытый документ. Может быть привязан к файлу или существовать
  без него (черновик). Хранит содержимое, кодировку, тип переноса строк, признак
  модификации, позиции курсоров, состояние отмены, метку времени файла на момент
  чтения.
- **`Session`** — снимок рабочего пространства: корни, буферы, порядок вкладок,
  активная вкладка, позиции прокрутки и курсоров.

Файлы могут быть открыты **вне любого корня** («свободные» буферы) — это обычный
сценарий, а не исключение.

## 4. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Оболочка | Tauri v2 | Системный WebView2 вместо своего Chromium: старт быстрее и установщик меньше, чем у Electron. Тяжёлая работа уходит в Rust. |
| Ядро | Rust | Файловый ввод-вывод, кодировки, обход дерева, индексация — там, где нужны предсказуемая скорость и отсутствие сборщика мусора. |
| Интерфейс | TypeScript + Svelte 5 | Svelte компилируется в прямые операции с DOM: нет рантайма виртуального DOM в бандле, что важно для цели по холодному старту. Для одного сопровождающего дешевле, чем ручное управление состоянием вкладок на голом TS. |
| Редактор | CodeMirror 6 | Виртуализация строк из коробки, модульность, отсутствие веса Monaco. |
| Подсветка | Tree-sitter | Этап 2. |
| Индекс | SQLite + FTS5 | Этап 2. |

### Версии инструментов

Зафиксированы на 2026-08-15: Rust 1.97.1 (msvc), Node 24.18.1, Tauri 2.11,
Svelte 5.56, Vite 8.2, TypeScript **6.0.3**, Vitest 4.1.

TypeScript намеренно не 7.x: `svelte-check` 4.7.6 объявляет peer-зависимость
`^5.0.0 || ^6.0.0` и с 7.x не работает. Вернуться к 7.x — когда обновится
`svelte-check`.

### Зависимости

Правило: перед добавлением библиотеки — обоснование, почему без неё нельзя.

**Подключены (Rust):** `tauri`, `tauri-build`, `serde`, `serde_json`.

**Согласованы, но ещё не подключены:**

| Крейт | Зачем | Почему не своими руками |
|---|---|---|
| `encoding_rs` | Декодеры/кодеры cp1251, cp1252, cp866, KOI8-R, UTF-16LE/BE | Своя реализация — таблица на каждую кодовую страницу плюс корректная работа с суррогатами UTF-16. Реализация из Firefox, без транзитивных зависимостей. |
| `windows-sys` | `ReplaceFileW`, `FlushFileBuffers`, атрибуты файла | Без этого инвариант 3 не выполняется (см. решение Р-006). |
| `toml` | Настройки и темы | Свой парсер TOML писать не будем. |

**Отклонены:**

| Крейт | Вместо него |
|---|---|
| `chardetng` | Свой определитель в `text/detect.rs`: метка порядка байтов → UTF-16 без метки по старшим байтам → строгая проверка на UTF-8 → оценка однобайтовых кандидатов (cp1251, cp866, KOI8-R, cp1252) по разрядам символов с наказанием за псевдографику, управляющие C1 и перевес заглавных. Надёжен на русском и западноевропейском, слабее на экзотических однобайтовых. Замена на библиотеку, если понадобится, — один вызов. |
| `notify` | На этапе 1 внешние изменения ловятся сравнением времени изменения и размера при получении фокуса окном и непосредственно перед записью — так делает Notepad++. Ноль зависимостей, ноль фоновых потоков. `notify` появится, когда понадобится живое дерево хранилища (этап 2). |

## 5. Расположение данных

Приложение не засоряет систему: по умолчанию все данные лежат рядом с
исполняемым файлом, как в портативном режиме.

```
<папка приложения>\
  zeronote.exe
  data\
    settings.toml      настройки, правится руками, кладётся в git
    keymap.toml        переназначение горячих клавиш
    themes\            пользовательские темы
    session.toml       снимок сессии
    drafts\            черновики несохранённых буферов
```

**Установка — только для текущего пользователя** (`%LOCALAPPDATA%\Programs\ZeroNote\`),
без прав администратора. Это обязательное условие: в `Program Files` папка
приложения недоступна на запись, и первый же сброс черновика провалился бы молча,
то есть инвариант 4 был бы нарушен.

**Проверка при старте:** приложение пробует реально создать и удалить файл в
`<папка приложения>\data\`. Успех — работаем портативно. Отказ (запуск с
read-only носителя, сетевой шары, из `Program Files` после ручного копирования) —
переходим на `%LOCALAPPDATA%\ZeroNote\` и **явно сообщаем об этом** в строке
состояния, а не молча.

**Деинсталлятор данные не трогает.** Удаление настроек и черновиков — отдельная
галочка, по умолчанию снята.

Разрешение путей — одна функция в `src-tauri/src/fsx/paths.rs`. Никаких путей,
собранных по месту в других модулях.

## 6. Измерения

Цели — часть спецификации, а не пожелание. Регрессия считается дефектом.
Числа умеренные намеренно: их задача — ловить деградацию, а не выжимать рекорды.

| Показатель | Цель |
|---|---|
| Холодный старт до готовности к вводу | ≤ 2000 мс |
| Тёплый старт | ≤ 800 мс |
| Открытие текстового файла 5 МБ | ≤ 500 мс |
| Ввод символа при открытом файле 10 МБ | без заметной задержки |
| Добавление хранилища на 10 000 файлов | интерфейс отзывчив, индексация в фоне |

**Политика больших файлов:** свыше 50 МБ — упрощённый режим: только чтение, без
подсветки, без индексации, виртуализированная прокрутка. Паритет с Notepad++ по
логам в сотни мегабайт в первом круге не требуется, но модель буфера не должна
делать такой режим невозможным в будущем.

### Методика

Замеры выполняются только на релизной сборке:

```
npm run tauri build
powershell -File bench\perf.ps1
```

**Что считается «готов к вводу»:** фронтенд смонтирован, первый кадр отрисован
(двойной `requestAnimationFrame`), окно показано. Окно создаётся скрытым и
показывается ровно в этот момент — это заодно убирает белую вспышку пустого
вебвью при старте.

Определение будет **уточняться** по мере появления функциональности: с задачи 4
точка сместится на «редактор смонтирован и получил фокус», с задачи 5 — на
«сессия восстановлена». Числа до и после такого уточнения впрямую несравнимы;
момент смены отмечается в таблице ниже.

**Про холодный старт.** Программно сбросить кэш файловой системы и рабочий набор
нельзя без прав администратора, да и это не воспроизвело бы состояние после
перезагрузки. За холодный принимается первый запуск после загрузки системы:
скрипт запускается сразу после перезагрузки, берётся строка «первый запуск».
Остальные запуски дают тёплый старт, из них берётся медиана.

Стенд собран внутри основного бинарника намеренно: измерять нужно ровно тот
исполняемый файл, который получит пользователь. Включается только аргументами
`--bench startup|ipc` и `--bench-out <путь>`; без них не делает ничего.

### Результаты

Машина замеров: Windows 11 Enterprise LTSC 2024 (10.0.26100).

| Дата | Что | Первый запуск | Тёплый (медиана) | Тёплый (мин) |
|---|---|---|---|---|
| 2026-08-15 | Задача 1: пустой каркас, редактора нет | 658 мс | 359 мс | 342 мс |
| 2026-08-15 | Задача 2: + чтение настроек, сборка темы, применение токенов | 391 мс | 381 мс | 366 мс |
| 2026-08-15 | Задача 3: + текстовое ядро (на старт не влияет) | 390 мс | 373 мс | 343 мс |

Из них время от входа в `main()`: задача 1 — 593 / 330 / 311 мс,
задача 2 — 342 / 344 / 330 мс. Разница с полным временем — загрузчик Windows
и создание процесса.

**Задача 2 добавила ~22 мс** к тёплому старту: чтение `settings.toml`, разбор
темы, сборка полусотни значений, один обход IPC и выставление свойств на `:root`.
Определение готовности при этом ужесточилось — теперь в него входит применённая
тема. Цель 800 мс не под угрозой.

Числа «первого запуска» в обеих строках занижены: бинарник был тёплым после
сборки. Честное число холодного старта снимается отдельным прогоном сразу после
перезагрузки системы.

Оба числа с большим запасом внутри целей (2000 / 800 мс). Запас нужен: на каркасе
ещё нет ни редактора, ни восстановления сессии, ни чтения настроек. Строка —
базовая линия, от которой отсчитывается деградация в следующих задачах.

Оговорка: «первый запуск» здесь — первый в прогоне стенда, не первый после
перезагрузки системы. Настоящее число холодного старта берётся отдельным
прогоном сразу после перезагрузки; до этого 658 мс — оценка снизу.

Путь целиком в ядре: чтение с диска → определение кодировки → раскодирование →

## 7. Оформление

Механика оформления — часть архитектуры, а не косметика. Устаревший и
неподатливый интерфейс — одна из главных причин ухода со старого софта.

### Принципы

- **Все визуальные величины — токены.** Ни одного цвета, отступа, радиуса, тени
  или размера шрифта, зашитого в код компонента. Только CSS-переменные, собранные
  в один слой: палитра, типографика, метрика, глубина. Тема — набор значений
  токенов, ничего больше.
- **Тема — файл, а не сборка.** Отдельный файл в папке пользователя,
  подхватывается без пересборки и применяется без перезапуска. Формат — TOML.
- **Светлая и тёмная с первого дня**, плюс следование системной настройке. Если
  что-то выглядит правильно только в одной — это дефект токенов.
- **Иконки — заменяемый слой.** Подключаются через единый реестр по логическим
  именам (`file.markdown`, `action.save`), а не вставляются в разметку. Смена
  набора не требует правок в компонентах.
- **Плотность и типографика — настройки пользователя:** компактный/обычный режим,
  шрифт и размер отдельно для редактора и для интерфейса, лигатуры вкл/выкл.
- **Компоновка изменяема:** боковая панель слева или справа, панели скрываются,
  элементы строки состояния настраиваются, горячие клавиши переназначаются.
- **Настройки в файле.** Всё настраиваемое — в читаемом конфиге, который можно
  править руками и класть в git. Интерфейс настроек — надстройка над файлом.

**Ограничение:** гибкость не должна протекать в код компонентов. Если добавление
новой настройки требует условий и ветвлений по всему интерфейсу — архитектура
выбрана неверно.

**Красота ≠ настраиваемость.** Настраиваемость закладывается с начала. Работа над
красивой темой по умолчанию — этап полировки. До тех пор базовая тема сдержанная
и нейтральная.

### Два уровня токенов

Разделение принципиальное, из него следует всё остальное.

1. **Палитра** — сырые цвета: `bg-0`, `fg-1`, `accent`, `border`. Их задаёт тема,
   и только тема. **В CSS они не попадают вовсе.**
2. **Семантические роли** — `color-bg-canvas`, `color-fg-muted`,
   `color-border-default`. Только их видят компоненты. Компонент не знает, какой
   именно серый ему достался.

Выражения ролей через палитру одинаковы для светлой и тёмной темы и живут в
`src-tauri/src/theme/tokens.rs`. Поэтому **тема на практике — это один раздел
`[palette]` из полутора десятков строк**, а не перечисление всех ролей.

### Где что лежит

| Что | Где |
|---|---|
| Канонический список токенов и значения по умолчанию | `src-tauri/src/theme/tokens.rs` |
| Разбор тем, сборка итоговых значений | `src-tauri/src/theme/mod.rs` |
| Встроенные темы | `src-tauri/src/theme/builtin/{light,dark}.toml` |
| Объявление токенов в CSS | `src/theme/tokens.css` |
| Применение к документу | `src/theme/apply.ts` |
| Реестр иконок | `src/icons/registry.ts` |

Список токенов задан в Rust, а объявлен в CSS; тест `tests/tokens.test.ts`
сверяет, что наборы имён совпадают ровно. Значения расходиться могут — они всё
равно перезаписываются при старте.

**Вся логика оформления — в Rust.** Фронтенд получает готовую плоскую таблицу
«имя токена → значение CSS» и выставляет её на `:root`. Ни одного правила выбора
цвета на стороне интерфейса нет. Это то же разделение обязанностей, что и с
файловым вводом-выводом.

### Порядок наложения значений

```
база → метрики плотности → семантические роли → тема → настройки пользователя
                                                            ↓
                                              раскрытие ссылок {palette.ключ}
```

Настройки идут после темы намеренно: выбранный пользователем шрифт интерфейса не
должен сбрасываться при смене темы.

### Формат файла темы

TOML, кладётся в `<данные>/themes/`. Минимальная рабочая тема:

```toml
schema = 1
id = "мой-вариант"
name = "Мой вариант"
appearance = "dark"        # light | dark — какие умолчания брать за основу

[palette]
bg-0 = "#101418"
accent = "#ff8800"
```

Не заданные цвета палитры берутся из встроенной темы того же вида, поэтому тема
из пяти строк работоспособна и не разваливается на неописанных ролях.

Разделы `[color]`, `[font]`, `[space]`, `[radius]`, `[border]`, `[shadow]`,
`[motion]`, `[z]`, `[control]` позволяют точечно переопределить конкретные роли.
Имя раздела становится префиксом токена: `[color] bg-canvas` → `color-bg-canvas`.
Значение может ссылаться на палитру — `"{palette.accent}"` — в том числе внутри
составного значения вроде тени.

Опечатка в имени раздела или токена — **ошибка с указанием имени**, а не молчаливое
«не применилось». Файл правится руками, и молчание здесь недопустимо.

### Плотность

Реализована подменой значений метрик, а не ветвлением в CSS. Профили `normal` и
`compact` описывают **один и тот же набор ключей** (это проверяет тест) — иначе
при переключении часть токенов осталась бы со значениями от прошлого режима.
Ни один компонент про режимы не знает.

### Смена без перезапуска

Три источника изменений:

1. **Системная тема** — ловится в вебвью медиазапросом `prefers-color-scheme`.
   Спрашивать Windows из Rust не нужно.
2. **Правка `settings.toml` или файла темы** — фоновый поток в Rust сравнивает
   время изменения и размер файлов дважды в секунду и присылает событие.
3. Появление или удаление файла темы — там же.

Событие пустое: в ответ фронтенд запрашивает состояние оформления целиком.
Так исключается расхождение между присланным и лежащим на диске.

## 10. Журнал решений

Каждое существенное решение попадает сюда в том же коммите, что и код.

### Р-001 · 2026-08-15 · Svelte 5 как фреймворк интерфейса

Стек задавал TypeScript, но не фреймворк. Выбран Svelte 5: компилируется в прямые
операции с DOM, нет рантайма виртуального DOM в бандле — это работает на цель по
холодному старту. Голый TS отвергнут: ручное управление состоянием вкладок и
панелей быстро станет источником багов у одного сопровождающего. React отвергнут
как более тяжёлый без выигрыша для этой задачи.

### Р-002 · 2026-08-15 · Владение содержимым буфера — по результатам замера

CodeMirror 6 хранит документ в JS. Держать вторую копию в Rust означает два
источника истины и постоянную задачу их согласования.

Рабочая гипотеза: для редактируемых буферов источник истины — фронтенд; Rust
владеет байтами при чтении и записи, метаданными (кодировка, EOL, время
изменения) и получает текст целиком при сохранении и при сбросе черновика.
Режим свыше 50 МБ — отдельный вид буфера, **только для чтения**, данные тянутся
из Rust страницами и в JS целиком не попадают; именно потому, что он read-only,
задачи согласования там не возникает, и путь к файлам в сотни мегабайт остаётся
открытым.

Альтернатива — зеркало документа в Rust с передачей дельт — честнее и
масштабируемее, но заметно дороже в реализации.

Решение принималось по замеру стоимости переноса 10 МБ через границу IPC. Замер
вынесен в задачу 1 намеренно: проверять архитектурную гипотезу на пустом каркасе
дешевле, чем переделывать написанный редактор. Числа — в разделе 6.

**Итог: гипотеза подтверждена, зеркало документа в Rust не нужно.**

- Rust → фронтенд, 10 МиБ: 69 мс (ASCII) / 88 мс (кириллица). Это путь открытия
  файла. При цели 500 мс на файл 5 МБ (там 40–45 мс) запас кратный.
- 1 МиБ — 8–9 мс в любом направлении. Заметки такого размера — типичный случай,
  и там разговора о дельтах нет вовсе.

**Известное узкое место, зафиксировано осознанно.** Обратное направление
(фронтенд → Rust) стоит вдвое-втрое дороже: 158 мс на 10 МиБ. Причина — аргумент
команды сериализуется в JSON на стороне JS. Это путь сброса черновика и
сохранения, и он идёт по основному потоку. То есть на буфере в 10 МБ через
~2 с после последней правки будет подвисание порядка 150 мс.

Для типичных заметок это неощутимо. Если станет мешать — два рычага, ни один из
которых не требует менять владение содержимым:

1. Передавать полезную нагрузку `ArrayBuffer`, а не строкой: Tauri v2 пропускает
   бинарные аргументы мимо JSON. Судя по разнице колонок «JSON» и «байты»
   в прямом направлении, это снимает заметную часть стоимости.
2. Сбрасывать в черновик не весь буфер, а изменённые участки.

Проверить рычаг 1 — в задаче 5, если замер сброса черновика упрётся в потолок.
Отдельная строка TODO там же.

### Р-003 · 2026-08-15 · TOML для настроек и тем

Файлы правятся руками и кладутся в git, значит нужны комментарии — JSON их не
поддерживает. YAML даёт лишнюю сложность и неоднозначность. Плоские секции TOML
хорошо ложатся на набор токенов. Крейт `toml` небольшой.

### Р-004 · 2026-08-15 · История отмены не переживает перезапуск

Модель требует хранить состояние отмены на буфере, но сериализовать его в сессию
не будем: снимок стека отмены CodeMirror привязал бы формат сессии к внутренностям
библиотеки и сделал бы запись черновика O(история) вместо O(текст).

Отмена живёт только в памяти. В сессии — содержимое, курсоры, прокрутка,
кодировка, тип переносов. Восстановление отмены — в «Отложено».

### Р-005 · 2026-08-15 · Одно окно на этапе 1, формат сессии — список

Этап 1 делает одно окно. Но сессия сериализуется как список рабочих пространств
с одним элементом, чтобы появление второго окна потом не ломало формат файла
сессии у существующих пользователей.

### Р-006 · 2026-08-15 · `ReplaceFileW` и единственный `unsafe`

`std::fs::rename` на Windows вызывает `MoveFileEx`, и целевой файл получает права
и атрибуты **временного** файла — теряются унаследованные ACL, альтернативные
потоки данных, время создания. Это прямое нарушение инварианта 3.

Правильный примитив — `ReplaceFileW`: переносит содержимое, но сохраняет
дескриптор безопасности, атрибуты и время создания приёмника. Доступен только
через FFI, поэтому потребует одного `unsafe`-блока в `src-tauri/src/fsx/atomic_save.rs`
с подробным комментарием. Это единственный запланированный `unsafe` на этапе 1.

### Р-007 · 2026-08-15 · Установщик без подписи

Сертификат подписи кода не планируется. Неподписанный установщик даёт экран
SmartScreen. В README — раздел с объяснением и SHA-256 сборки, чтобы тестировщики
могли сверить файл.

### Р-008 · 2026-08-15 · Данные рядом с приложением, установка для пользователя

См. раздел 5. Требование «не засорять систему» выполняется хранением данных рядом
с exe. Чтобы это не нарушало инвариант 4, установка идёт только для текущего
пользователя, а при недоступности папки на запись приложение переходит на
`%LOCALAPPDATA%` с явным уведомлением.

### Р-009 · 2026-08-15 · `panic = "abort"` не включаем

Профиль релиза оптимизирован под скорость (`opt-level = 3`, `lto`,
`codegen-units = 1`), но `panic = "abort"` сознательно не включён: паника в
обработчике команды не должна убивать процесс вместе с несохранёнными
черновиками (инвариант 4).

### Р-010 · 2026-08-15 · Git не нормализует переносы строк

На машине разработчика включён `core.autocrlf`, и git при первом же
`git add` собрался приводить LF к CRLF в рабочей копии.

Для этого проекта такая нормализация — прямая угроза инварианту 1. В
`src-tauri/tests/fixtures/` будут лежать эталонные файлы с намеренно разными
переносами (CRLF, LF, смешанные) и с намеренным наличием или отсутствием
финальной новой строки. Если git станет их править, эталоны перестанут быть
эталонами, а тесты инварианта 1 будут проверять не то, что нужно, — и при этом
останутся зелёными. Поломка почти незаметная и очень дорогая.

Добавлен `.gitattributes` с `* -text`: никакой конверсии, ни для одного файла,
независимо от настроек git у того, кто клонирует репозиторий.

### Р-011 · 2026-08-15 · Тема — только палитра, роли выводятся

Первая мысль была сделать тему плоским перечислением всех токенов. Отвергнута:
такая тема — это восемь десятков строк, которые надо держать в согласии между
собой, и написать её вручную практически невозможно.

Введены два уровня: палитра (сырые цвета, задаёт тема) и семантические роли
(выводятся из палитры выражениями, общими для светлой и тёмной темы). Палитра
в CSS не попадает — компоненты видят только роли.

Цена: лишний слой в голове. Выигрыш: рабочая тема пишется за пять минут, а
компонент физически не может сослаться на «серый номер три».

### Р-012 · 2026-08-15 · Плотность — подмена значений, не ветвление в CSS

Компактный режим мог быть сделан классом на корне и правилами
`[data-density="compact"] .tabbar { ... }` в каждом компоненте. Это ровно то
«протекание гибкости в код компонентов», которое запрещено: каждая новая
настройка добавляла бы ветвление в интерфейс.

Вместо этого плотность — второй профиль значений метрик, собираемый в Rust.
Компоненты про режимы не знают вовсе. Профили обязаны описывать одинаковый
набор ключей, это проверяет тест.

### Р-013 · 2026-08-15 · Приложение настройки только читает

`settings.toml` правится руками и кладётся в git, значит комментарии в нём —
половина пользы. Сериализация через serde комментарии не переживает: первая же
запись из приложения стёрла бы все пояснения и форматирование пользователя.

Поэтому на этом этапе приложение файл только читает, а изменения подхватывает
на лету. Смена темы «без перезапуска» этим полностью обеспечена.

Когда появится окно параметров, понадобится запись с сохранением комментариев —
это делает крейт `toml_edit` (тот же, что использует cargo). Брать его сейчас
незачем: писать пока нечего.

### Р-014 · 2026-08-15 · Слежение за файлами опросом, без `notify`

Правка темы должна применяться на лету. Крейт `notify` для этого не берём
(см. раздел 4): речь о паре десятков маленьких файлов, которые фоновый поток
опрашивает дважды в секунду. Затраты неизмеримы, зависимостей ноль.

В слепок входит не только время изменения, но и размер: файловые системы
Windows хранят время с грубым шагом, и быстрая правка может не сдвинуть отметку.

### Р-015 · 2026-08-15 · Запрет зашитых величин — тест, а не договорённость

`tests/tokens.test.ts` разбирает блоки `<style>` всех компонентов и все файлы
CSS кроме слоя токенов и валит сборку на:

* шестнадцатеричном цвете;
* цветовой функции `rgb()`, `hsl()`, `color-mix()` и подобных;
* цвете по имени (`black`, `red`, …);
* абсолютной величине с единицами `px`, `rem`, `em`, `pt`, `ms`, `s`;
* значении `line-height`, `z-index`, `font-weight`, `box-shadow`,
  `transition-duration`, `transition-timing-function` не через токен.

Разрешены `%`, `fr`, `vh`, `vw`, `ch`, безразмерный ноль и ключевые слова
(`auto`, `none`, `inherit`, `currentColor`, `transparent`).

Проверено, что сторож действительно ловит нарушение: временный компонент с
пятью видами зашитых значений валит тест на всех пяти.

### Р-016 · 2026-08-15 · Свой заголовок окна

Системный заголовок отвергнут в пользу собственного, как в VS Code. Причина —
он остаётся вне темы: приложение может быть янтарным, а полосу заголовка рисует
Windows в системной теме. Плюс своя полоса даёт место под вкладки и меню и
возможность вешать на неё поведение.

Цена, принятая сознательно: перетаскивание окна, двойной клик для разворота,
прилипание к краям (Aero Snap), кнопки окна, меню и реакция на изменение
системного масштаба — всё реализуется вручную. Это класс дефектов, которые
заметны каждому тестировщику.

Решение принято до задачи 4 намеренно: полоса вкладок живёт внутри заголовка,
то есть это меняет компоновку оболочки, которую задача 4 наполняет. Принимать
его после задачи 4 значило бы переделывать.

Реализация — задача 4. `decorations: false` в `tauri.conf.json` и своя полоса
поверх; область перетаскивания помечается `data-tauri-drag-region`.

### Р-017 · 2026-08-15 · Авторство и правообладание разведены

Проект пишется в паре человеком и моделью, и это отражено в README, `Cargo.toml`
и `package.json` — там указаны оба участника.

Строка copyright в LICENSE при этом называет только Mark Karte. Заявление о

### Р-018 · 2026-08-15 · Смешанные переносы строк — решение пользователя

Внутри буфера все переносы одинаковы (`\n`): этого требует CodeMirror, который
хранит строки без завершителей и склеивает их одним разделителем. Значит для
файла со смешанными переносами не существует способа записать его обратно
байт в байт после правки.

Молча привести такой файл к преобладающему типу — прямое нарушение инварианта 1:
это нормализация без явной команды, причём затрагивающая каждую строку файла.

Принято:

* факт смешения определяется точно, с подсчётом каждого типа;
* он виден снаружи (`EolInfo.mixed`) и будет показан в строке состояния;
* функция записи **требует явно указать** тип переноса — взять его «по
  умолчанию из файла» нельзя, потому что умолчания нет;
* нетронутый буфер не сохраняется вовсе, поэтому просто открыть и закрыть
  такой файл безопасно.

### Р-019 · 2026-08-15 · UTF-16 без метки определяется по старшим байтам

Наивная проверка «много нулевых байтов через один» ловит только латиницу.
Кириллица в UTF-16LE — это байты вида `21 04`, оба меньше `0x80`, нулей там нет
вовсе. Такой файл проходил проверку «весь в пределах ASCII» и объявлялся UTF-8,
превращаясь в кашу из управляющих символов. Дефект найден тестом при написании,
до того как попал куда-либо ещё.

Проверяется другое: байты одной чётности почти все меньше `0x08` (это старшие
байты кодовых единиц для латиницы, кириллицы, греческого, иврита, арабского),
а байты другой чётности разнообразны. Проверка идёт **до** всех остальных.

Ограничение, принятое сознательно: файл в UTF-16 без метки, состоящий в основном
из иероглифов или эмодзи, так не опознается. Такие файлы практически всегда идут
с меткой, а без неё кодировку можно выбрать вручную.

### Р-020 · 2026-08-15 · Непереводимый символ — ошибка до записи

Если в тексте есть символ, которого нет в кодировке файла (русское слово в файле
windows-1252), запись отвергается с указанием конкретного символа. Заменять его
на вопросительный знак, как делают многие редакторы, нельзя: это порча чужого
файла, о которой пользователь узнаёт слишком поздно.

Симметрично при чтении: если в байтах есть недопустимые для кодировки
последовательности, документ помечается `lossy`, и об этом надо сообщить до
сохранения — обратная запись байт в байт уже невозможна.

### Р-021 · 2026-08-15 · Эталоны лежат в репозитории и создаются генератором

`src-tauri/tests/fixtures/` содержит 17 настоящих файлов: все кодировки, обе
метки, все три типа переносов, файл без финальной новой строки, пустой файл,
файл из одной метки, frontmatter, смешанные переносы.

Создаются командой `cargo run --example make_fixtures`, но пересоздавать их без
причины не следует — они и есть эталон. Генератор существует, чтобы набор можно
было воспроизвести и расширить.

От нормализации переносов их защищает `.gitattributes` (решение Р-010). Без него
эталоны перестали бы быть эталонами, а тесты остались бы зелёными.

## 11. План этапа 1

Единственная цель ближайших работ. Всё, что не входит сюда, — не сейчас.

| № | Задача | Состояние |
|---|---|---|
| 1 | Каркас, документы, измерительный стенд | готово |

Задача 2 идёт раньше интерфейса намеренно: каждый компонент, написанный после
неё, наследует дисциплину токенов автоматически. В обратном порядке пришлось бы
вычищать зашитые величины из уже написанного кода.

### Критерии готовности этапа

- Инварианты 1–5 покрыты автоматическими тестами.
- Целевые показатели производительности замерены и записаны в разделе 6.
- В коде компонентов нет ни одного зашитого цвета или размера.
- Собран установочный пакет, который можно отдать тестировщику.
- В редакторе можно работать целый день вместо Notepad++.
