## 1. Что это

Редактор, который совмещает две вещи, сегодня живущие раздельно:

1. Быстрый универсальный текстовый редактор уровня Notepad++ — мгновенный старт,
   любые файлы, любые кодировки, поиск с регулярными выражениями.
2. Папка заметок открывается как проект — включая хранилище Obsidian,
   несколько проектов одновременно в одном окне (модель VS Code / PlatformIO).
   Формат проекта свой, чужой не разбирается: решение Р-022.

Целевой пользователь — разработчик, у которого заметки и код лежат рядом.

### Границы первого круга

В работе: только Windows 10/11, только локальная файловая система.

Явно вне области — не реализовывать и не закладывать: синхронизация и облако,
Linux, Android, шифрованные контейнеры, менеджер паролей, плагинный API, макросы,
пользовательские синтаксисы (UDL), LSP и автодополнение, сравнение файлов,
FTP/SFTP, совместное редактирование.

## 3. Модель данных

- **`Workspace`** — одно окно. Список корней и список открытых буферов.
  Сериализуется целиком как сессия.
- **`Root`** — корневая папка, добавленная в рабочее пространство. Собственные
  правила игнорирования и собственный индекс. Если рядом лежит файл проекта
  ZeroNote — берёт настройки оттуда (см. решение Р-022).
- **`Buffer`** — открытый документ. Может быть привязан к файлу или существовать
  без него (черновик). Хранит содержимое, кодировку, тип переноса строк, признак
  модификации, позиции курсоров, состояние отмены, метку времени файла на момент
  чтения.
- **`Session`** — снимок рабочего пространства: корни, буферы, порядок вкладок,
  активная вкладка, позиции прокрутки и курсоров.

Файлы могут быть открыты **вне любого корня** («свободные» буферы) — это обычный
сценарий, а не исключение.

- **`Project`** — файл `zeronote.toml` в корне папки. Наш формат, не чужой:
  имя проекта, правила игнорирования, настройки редактора на проект.
  Подробности — решение Р-022. Сделано задачей 9.

  Приложение этот файл **не создаёт само** (Р-049): без него корень работает
  на умолчаниях. Правила игнорирования — семантика `.gitignore` (Р-050).

### Зависимости

Правило: перед добавлением библиотеки — обоснование, почему без неё нельзя.

`toml_edit` подключён задачей 20: окно параметров пишет в `settings.toml`,
а обычный `toml` через serde собирает документ заново из структуры и стирает
комментарии пользователя. Тот же крейт правит `Cargo.toml` у cargo. Последний
обоснован решением Р-050 и подключён задачей 9; на задаче 10 оттуда же берётся
обход дерева.

**Подключены (фронтенд):** `@codemirror/state`, `view`, `commands`, `search`,
`language`, `@tauri-apps/api`, `@tauri-apps/plugin-dialog`, плюс языковые
пакеты подсветки (задача 13): `lang-markdown`, `lang-cpp`, `lang-rust`,
`lang-javascript`, `lang-python`, `lang-json`, `lang-html`, `lang-css`,
`lang-xml` и `legacy-modes`. Последний — один пакет на семь простых языков
(toml, yaml, ini, sql, shell, powershell, lua), у которых своего Lezer-пакета

## 5. Расположение данных

Приложение не засоряет систему: по умолчанию все данные лежат рядом с
исполняемым файлом, как в портативном режиме.

```
<папка приложения>\
  zeronote.exe
  data\
    settings.toml      настройки, правится руками, кладётся в git
    keymap.toml        переназначение горячих клавиш
    themes\            пользовательские темы
    session.toml       снимок сессии
    recent.toml        недавно открытые файлы
    drafts\            черновики несохранённых буферов
```

**Установка — только для текущего пользователя**, в `%LOCALAPPDATA%\ZeroNote\`,
без прав администратора. Это обязательное условие: в `Program Files` папка
приложения недоступна на запись, и первый же сброс черновика провалился бы молча,
то есть инвариант 4 был бы нарушен.

Запасная папка — `%LOCALAPPDATA%\ZeroNote-data\`, **не** `%LOCALAPPDATA%\ZeroNote\`:
последняя и есть папка установки, и запасные данные оказались бы внутри неё.
Расхождение обнаружено при первой настоящей установке из пакета (задача 8).

**Проверка при старте:** приложение пробует реально создать и удалить файл в
`<папка приложения>\data\`. Успех — работаем портативно. Отказ (запуск с
read-only носителя, сетевой шары, из `Program Files` после ручного копирования) —
переходим на `%LOCALAPPDATA%\ZeroNote-data\` и **явно сообщаем об этом** в строке
состояния, а не молча.

**Деинсталлятор данные не трогает.** Удаление настроек и черновиков — отдельная
галочка, по умолчанию снята.

Разрешение путей — одна функция в `src-tauri/src/fsx/paths.rs`. Никаких путей,
собранных по месту в других модулях.

## 6. Измерения

Цели — часть спецификации, а не пожелание. Регрессия считается дефектом.
Числа умеренные намеренно: их задача — ловить деградацию, а не выжимать рекорды.

| Показатель | Цель |
|---|---|
| Холодный старт до готовности к вводу | ≤ 2000 мс |
| Тёплый старт | ≤ 800 мс |
| Открытие текстового файла 5 МБ | ≤ 500 мс |
| Ввод символа при открытом файле 10 МБ | без заметной задержки |
| Раскрытие папки с 10 000 записей | ≤ 300 мс |
| Добавление хранилища на 10 000 файлов | интерфейс отзывчив, индексация в фоне |
| Полная индексация 10 000 файлов | ≤ 30 с |
| Поиск по содержимому, первые результаты | ≤ 300 мс |

**Политика больших файлов:** свыше 50 МБ — упрощённый режим: только чтение, без
подсветки, без индексации, виртуализированная прокрутка. Паритет с Notepad++ по
логам в сотни мегабайт в первом круге не требуется, но модель буфера не должна
делать такой режим невозможным в будущем.

### Методика

Замеры выполняются только на релизной сборке:

```
npm run tauri build
powershell -File bench\perf.ps1
```

**Что считается «готов к вводу»:** фронтенд смонтирован, первый кадр отрисован
(двойной `requestAnimationFrame`), окно показано. Окно создаётся скрытым и
показывается ровно в этот момент — это заодно убирает белую вспышку пустого
вебвью при старте.

Определение будет **уточняться** по мере появления функциональности: с задачи 4
точка сместится на «редактор смонтирован и получил фокус», с задачи 5 — на
«сессия восстановлена». Числа до и после такого уточнения впрямую несравнимы;
момент смены отмечается в таблице ниже.

**Про холодный старт.** Программно сбросить кэш файловой системы и рабочий набор
нельзя без прав администратора, да и это не воспроизвело бы состояние после
перезагрузки. За холодный принимается первый запуск после загрузки системы:
скрипт запускается сразу после перезагрузки, берётся строка «первый запуск».
Остальные запуски дают тёплый старт, из них берётся медиана.

Стенд собран внутри основного бинарника намеренно: измерять нужно ровно тот
исполняемый файл, который получит пользователь. Включается только аргументами
`--bench startup|ipc|open|tree` и `--bench-out <путь>`; без них не делает ничего.

## 7. Оформление

Механика оформления — часть архитектуры, а не косметика. Устаревший и
неподатливый интерфейс — одна из главных причин ухода со старого софта.

### Принципы

- **Все визуальные величины — токены.** Ни одного цвета, отступа, радиуса, тени
  или размера шрифта, зашитого в код компонента. Только CSS-переменные, собранные
  в один слой: палитра, типографика, метрика, глубина. Тема — набор значений
  токенов, ничего больше.
- **Тема — файл, а не сборка.** Отдельный файл в папке пользователя,
  подхватывается без пересборки и применяется без перезапуска. Формат — TOML.
- **Светлая и тёмная с первого дня**, плюс следование системной настройке. Если
  что-то выглядит правильно только в одной — это дефект токенов.
- **Иконки — заменяемый слой.** Подключаются через единый реестр по логическим
  именам (`file.markdown`, `action.save`), а не вставляются в разметку. Смена
  набора не требует правок в компонентах.
- **Плотность и типографика — настройки пользователя:** компактный/обычный режим,
  шрифт и размер отдельно для редактора и для интерфейса, лигатуры вкл/выкл.
- **Компоновка изменяема:** боковая панель слева или справа, панели скрываются,
  элементы строки состояния настраиваются, горячие клавиши переназначаются.
- **Настройки в файле.** Всё настраиваемое — в читаемом конфиге, который можно
  править руками и класть в git. Интерфейс настроек — надстройка над файлом.

**Ограничение:** гибкость не должна протекать в код компонентов. Если добавление
новой настройки требует условий и ветвлений по всему интерфейсу — архитектура
выбрана неверно.

**Красота ≠ настраиваемость.** Настраиваемость закладывается с начала. Работа над
красивой темой по умолчанию — этап полировки. До тех пор базовая тема сдержанная
и нейтральная.

### Два уровня токенов

Разделение принципиальное, из него следует всё остальное.

1. **Палитра** — сырые цвета: `bg-0`, `fg-1`, `accent`, `border`. Их задаёт тема,
   и только тема. **В CSS они не попадают вовсе.**
2. **Семантические роли** — `color-bg-canvas`, `color-fg-muted`,
   `color-border-default`. Только их видят компоненты. Компонент не знает, какой
   именно серый ему достался.

Выражения ролей через палитру одинаковы для светлой и тёмной темы и живут в
`src-tauri/src/theme/tokens.rs`. Поэтому **тема на практике — это один раздел
`[palette]` из полутора десятков строк**, а не перечисление всех ролей.

### Где что лежит

| Что | Где |
|---|---|
| Канонический список токенов и значения по умолчанию | `src-tauri/src/theme/tokens.rs` |
| Разбор тем, сборка итоговых значений | `src-tauri/src/theme/mod.rs` |
| Встроенные темы | `src-tauri/src/theme/builtin/*.toml` |
| Объявление токенов в CSS | `src/theme/tokens.css` |
| Применение к документу | `src/theme/apply.ts` |
| Объявление вшитых шрифтов | `src/theme/fonts.css`, файлы — `src/theme/fonts/` |
| Реестр иконок | `src/icons/registry.ts` |

Список токенов задан в Rust, а объявлен в CSS; тест `tests/tokens.test.ts`
сверяет, что наборы имён совпадают ровно. Значения расходиться могут — они всё
равно перезаписываются при старте.

**Вся логика оформления — в Rust.** Фронтенд получает готовую плоскую таблицу
«имя токена → значение CSS» и выставляет её на `:root`. Ни одного правила выбора
цвета на стороне интерфейса нет. Это то же разделение обязанностей, что и с
файловым вводом-выводом.

### Порядок наложения значений

```
база → метрики плотности → семантические роли → тема → настройки пользователя
                                                            ↓
                                              раскрытие ссылок {palette.ключ}
```

Настройки идут после темы намеренно: выбранный пользователем шрифт интерфейса не
должен сбрасываться при смене темы.

### Формат файла темы

TOML, кладётся в `<данные>/themes/`. Минимальная рабочая тема:

```toml
schema = 1
id = "мой-вариант"
name = "Мой вариант"
appearance = "dark"        # light | dark — какие умолчания брать за основу

[palette]
bg-0 = "#101418"
accent = "#ff8800"
```

Не заданные цвета палитры берутся из встроенной темы того же вида, поэтому тема
из пяти строк работоспособна и не разваливается на неописанных ролях.

Разделы `[color]`, `[font]`, `[space]`, `[radius]`, `[border]`, `[shadow]`,
`[motion]`, `[z]`, `[control]` позволяют точечно переопределить конкретные роли.
Имя раздела становится префиксом токена: `[color] bg-canvas` → `color-bg-canvas`.
Значение может ссылаться на палитру — `"{palette.accent}"` — в том числе внутри
составного значения вроде тени.

Опечатка в имени раздела или токена — **ошибка с указанием имени**, а не молчаливое
«не применилось». Файл правится руками, и молчание здесь недопустимо.

### Встроенные темы

Семь, задача 17. Список канонический — `BUILTIN` в `theme/mod.rs`; тест
проверяет, что каждая разбирается, собирается целиком и задаёт всю палитру сама.

| id | Название | Вид | Про что она |
|---|---|---|---|
| `dark` | Графит | тёмная | основная тёмная, нейтральный серо-синий |
| `light` | Бумага | светлая | основная светлая |
| `midnight` | Полночь | тёмная | тёмно-синяя, пониженный контраст, для вечера |
| `nordic` | Нордик | тёмная | самые светлые фоны среди тёмных, приглушённый код |
| `pine` | Хвоя | тёмная | зелёная, зелёный акцент не спорит с синим кодом |
| `sepia` | Сепия | светлая | тёплая бумага для долгого чтения |
| `contrast` | Контраст | тёмная | чёрный фон, максимально разведённые цвета |

Идентификаторы `light` и `dark` сохранены с этапа 1: на них ссылаются
`settings.toml` пользователей и ключи `light_theme`/`dark_theme`. Поменялись
только названия.

Палитра темы — 26 цветов: пять фонов, три ступени текста и цвет поверх акцента,
акцент с двумя полупрозрачными подложками, две границы, три цвета состояний,
**шесть** цветов кода, два цвета тени и подложка модального окна.

Шесть, а не восемь: операторы, знаки препинания и заголовки markdown берут цвет
из общей палитры (Р-082). Автор темы подбирает меньше, а разница на экране
не теряется — заголовок отличается весом, оператор тише знака препинания.

### Читаемость проверяется, а не подразумевается

Тема, где серое по серому, — это не дело вкуса, а неработающая тема. Заметить
такое глазами можно только на своём экране при своём освещении, поэтому
`builtin_themes_are_readable` считает контраст по WCAG 2 для каждой встроенной
темы: основной текст ≥ 7:1, второстепенный, акцент и цвета состояний ≥ 4,5:1,
надпись на залитой акцентом кнопке ≥ 4,5:1. Оба фона, рабочая область и панель:
в светлых темах панель темнее рабочей области, в тёмных светлее, и слабое место
у них разное.

Тест поймал три случая при первом же прогоне — красный «Нордика» на фоне панели
давал 3,2:1, тёплые зелёный и жёлтый «Сепии» — 4,4:1. Все три я до этого считал
на глаз и считал верными.

### Шрифты

`IBM Plex Sans` для интерфейса, `JetBrains Mono` для редактора; вшиты файлами,
а не подключаются из сети (Р-075). Четыре файла `woff2`, 125 КБ: оба семейства
раздаются переменными шрифтами, поэтому один файл покрывает весь диапазон весов,
а латиница и кириллица разделены по `unicode-range` и грузятся порознь.

Подробности и порядок обновления — `src/theme/fonts/README.md`. Лицензия обоих —
SIL OFL 1.1, тексты лежат там же.

### Плотность

Реализована подменой значений метрик, а не ветвлением в CSS. Профили `normal` и
`compact` описывают **один и тот же набор ключей** (это проверяет тест) — иначе
при переключении часть токенов осталась бы со значениями от прошлого режима.
Ни один компонент про режимы не знает.

### Смена без перезапуска

Три источника изменений:

1. **Системная тема** — ловится в вебвью медиазапросом `prefers-color-scheme`.
   Спрашивать Windows из Rust не нужно.
2. **Правка `settings.toml` или файла темы** — фоновый поток в Rust сравнивает
   время изменения и размер файлов дважды в секунду и присылает событие.
3. Появление или удаление файла темы — там же.

Событие пустое: в ответ фронтенд запрашивает состояние оформления целиком.
Так исключается расхождение между присланным и лежащим на диске.

### Сочетания, которые приносит сам редактор

Кроме реестра, в окне действует набор `defaultKeymap` из CodeMirror. Эти
сочетания работают, но их нет ни в палитре, ни в меню, ни в `keymap.toml`:
переназначить их нельзя, и до задачи 41 о них не было записано нигде.

Оставлены за редактором намеренно (Р-122) — это примитивы правки и движения
курсора, а не команды приложения:

| Сочетание | Что делает | Как в VS Code |
|---|---|---|
| `Alt+↑` / `Alt+↓` | переместить строку | да |
| `Shift+Alt+↑` / `Shift+Alt+↓` | продублировать строку вверх или вниз | да |
| `Ctrl+Alt+↑` / `Ctrl+Alt+↓` | поставить курсор строкой выше или ниже | да |
| `Ctrl+[` / `Ctrl+]` | снять или добавить отступ | да |
| `Ctrl+Enter` | пустая строка под текущей | да |
| `Ctrl+M` | `Tab` переходит по элементам, а не отступает | да |
| `Escape` | свести курсоры к одному | да |
| `Ctrl+I` | расширить выделение по разбору языка | нет |
| `Alt+L` | выделить строку | нет |
| `Alt+A` | закомментировать блоком | нет |

Проверено на живом приложении, а не взято из чужой документации: `Alt+↑`,
`Shift+Alt+↓` и `Ctrl+Shift+K` нажаты в отладочной сборке, и каждое сделало
то, что здесь написано.

**Известное расхождение внутри пары.** `Alt+↑` от CodeMirror двигает все
выделенные строки и работает с несколькими курсорами; наша `edit.move-line-up`
на `Ctrl+Shift+↑` двигает только строку главного курсора. То есть два
сочетания «одного и того же» ведут себя по-разному. Наша реализация тут
не лучше, а беднее: множественные курсоры она молча игнорирует, хотя весь
остальной модуль `editor/commands.ts` с ними работает. Чинится заменой нашей
реализации на `moveLineUp`/`moveLineDown` из CodeMirror — отдельной задачей,
со своим тестом.

Формат файла переназначения:

```toml
schema = 1

[bindings]
"ctrl+shift+d" = "edit.duplicate-line"   # добавить своё
"ctrl+l" = ""                            # снять стандартное
```

Порядок частей и регистр не важны: `Shift+Ctrl+D` и `ctrl+shift+d` — одно и то же.
Опечатка в имени команды или в сочетании называется по имени и показывается
полосой предупреждений; раскладка при этом остаётся рабочей на умолчаниях.

**Отбираем у вебвью** сочетания, которые он считает своими, даже если своей
команды на них пока нет: `F5` и `Ctrl+R` перезагружают страницу и стирают
несохранённые буферы, `Ctrl+P` — системную печать, `Ctrl+J`, `Ctrl+±`, `Ctrl+0`
и масштабирование колесом меняют масштаб всего интерфейса.

**В поле ввода команды `edit.*` не срабатывают** (решение Р-040): `Ctrl+A`
в строке поиска должен выделять её содержимое, а не весь документ. Остальные
команды — сохранение, поиск, переключение вкладок — работают отовсюду: это
действия над приложением, а не над текстом под курсором.

**`Alt` с цифрой на дополнительной клавиатуре сочетанием не считается**
(решение Р-111): это системный ввод знака по коду, `Alt+0151` — тире.
Цифра верхнего ряда сочетанием остаётся, на ней и висит свёртка.

**А `Ctrl+X`, `Ctrl+C` и `Ctrl+V` не срабатывают нигде** — их выполняет сам
вебвью, и выполняет правильно (решение Р-108). Команды в таблице стоят ради
меню и палитры: пункт меню нажатием клавиши не является, а подпись сочетания
в нём обязана приходить из раскладки. Переназначить их можно, и тогда новое
сочетание выполняем уже мы.

## 10. Журнал решений

Каждое существенное решение попадает сюда в том же коммите, что и код.

### Р-001 · 2026-08-15 · Svelte 5 как фреймворк интерфейса

Стек задавал TypeScript, но не фреймворк. Выбран Svelte 5: компилируется в прямые
операции с DOM, нет рантайма виртуального DOM в бандле — это работает на цель по
холодному старту. Голый TS отвергнут: ручное управление состоянием вкладок и
панелей быстро станет источником багов у одного сопровождающего. React отвергнут
как более тяжёлый без выигрыша для этой задачи.

### Р-002 · 2026-08-15 · Владение содержимым буфера — по результатам замера

CodeMirror 6 хранит документ в JS. Держать вторую копию в Rust означает два
источника истины и постоянную задачу их согласования.

Рабочая гипотеза: для редактируемых буферов источник истины — фронтенд; Rust
владеет байтами при чтении и записи, метаданными (кодировка, EOL, время
изменения) и получает текст целиком при сохранении и при сбросе черновика.
Режим свыше 50 МБ — отдельный вид буфера, **только для чтения**, данные тянутся
из Rust страницами и в JS целиком не попадают; именно потому, что он read-only,
задачи согласования там не возникает, и путь к файлам в сотни мегабайт остаётся
открытым.

Альтернатива — зеркало документа в Rust с передачей дельт — честнее и
масштабируемее, но заметно дороже в реализации.

Решение принималось по замеру стоимости переноса 10 МБ через границу IPC. Замер
вынесен в задачу 1 намеренно: проверять архитектурную гипотезу на пустом каркасе
дешевле, чем переделывать написанный редактор. Числа — в разделе 6.

**Итог: гипотеза подтверждена, зеркало документа в Rust не нужно.**

- Rust → фронтенд, 10 МиБ: 69 мс (ASCII) / 88 мс (кириллица). Это путь открытия
  файла. При цели 500 мс на файл 5 МБ (там 40–45 мс) запас кратный.
- 1 МиБ — 8–9 мс в любом направлении. Заметки такого размера — типичный случай,
  и там разговора о дельтах нет вовсе.

**Известное узкое место, зафиксировано осознанно.** Обратное направление
(фронтенд → Rust) стоит вдвое-втрое дороже: 158 мс на 10 МиБ. Причина — аргумент
команды сериализуется в JSON на стороне JS. Это путь сброса черновика и
сохранения, и он идёт по основному потоку. То есть на буфере в 10 МБ через
~2 с после последней правки будет подвисание порядка 150 мс.

Для типичных заметок это неощутимо. Если станет мешать — два рычага, ни один из
которых не требует менять владение содержимым:

1. Передавать полезную нагрузку `ArrayBuffer`, а не строкой: Tauri v2 пропускает
   бинарные аргументы мимо JSON. Судя по разнице колонок «JSON» и «байты»
   в прямом направлении, это снимает заметную часть стоимости.
2. Сбрасывать в черновик не весь буфер, а изменённые участки.

Проверить рычаг 1 — в задаче 5, если замер сброса черновика упрётся в потолок.
Отдельная строка TODO там же.

### Р-006 · 2026-08-15 · `ReplaceFileW` и первый `unsafe`

`std::fs::rename` на Windows вызывает `MoveFileEx`, и целевой файл получает права
и атрибуты **временного** файла — теряются унаследованные ACL, альтернативные
потоки данных, время создания. Это прямое нарушение инварианта 3.

Правильный примитив — `ReplaceFileW`: переносит содержимое, но сохраняет
дескриптор безопасности, атрибуты и время создания приёмника. Доступен только
через FFI, поэтому потребует одного `unsafe`-блока в `src-tauri/src/fsx/atomic_save.rs`
с подробным комментарием. Это единственный запланированный `unsafe` на этапе 1.

Второй и третий появились на этапе 5 и по той же причине — нужного нет иначе
как через системный вызов: чтение буфера обмена (`src-tauri/src/clipboard.rs`,
Р-109) и удаление в корзину (`src-tauri/src/fsx/recycle.rs`, Р-110).

### Р-010 · 2026-08-15 · Git не нормализует переносы строк

На машине разработчика включён `core.autocrlf`, и git при первом же
`git add` собрался приводить LF к CRLF в рабочей копии.

Для этого проекта такая нормализация — прямая угроза инварианту 1. В
`src-tauri/tests/fixtures/` будут лежать эталонные файлы с намеренно разными
переносами (CRLF, LF, смешанные) и с намеренным наличием или отсутствием
финальной новой строки. Если git станет их править, эталоны перестанут быть
эталонами, а тесты инварианта 1 будут проверять не то, что нужно, — и при этом
останутся зелёными. Поломка почти незаметная и очень дорогая.

Добавлен `.gitattributes` с `* -text`: никакой конверсии, ни для одного файла,
независимо от настроек git у того, кто клонирует репозиторий.

### Р-011 · 2026-08-15 · Тема — только палитра, роли выводятся

Первая мысль была сделать тему плоским перечислением всех токенов. Отвергнута:
такая тема — это восемь десятков строк, которые надо держать в согласии между
собой, и написать её вручную практически невозможно.

Введены два уровня: палитра (сырые цвета, задаёт тема) и семантические роли
(выводятся из палитры выражениями, общими для светлой и тёмной темы). Палитра
в CSS не попадает — компоненты видят только роли.

Цена: лишний слой в голове. Выигрыш: рабочая тема пишется за пять минут, а
компонент физически не может сослаться на «серый номер три».

### Р-012 · 2026-08-15 · Плотность — подмена значений, не ветвление в CSS

Компактный режим мог быть сделан классом на корне и правилами
`[data-density="compact"] .tabbar { ... }` в каждом компоненте. Это ровно то
«протекание гибкости в код компонентов», которое запрещено: каждая новая
настройка добавляла бы ветвление в интерфейс.

Вместо этого плотность — второй профиль значений метрик, собираемый в Rust.
Компоненты про режимы не знают вовсе. Профили обязаны описывать одинаковый
набор ключей, это проверяет тест.

### Р-013 · 2026-08-15 · Приложение настройки только читает

`settings.toml` правится руками и кладётся в git, значит комментарии в нём —

Поэтому на этом этапе приложение файл только читает, а изменения подхватывает

Когда появится окно параметров, понадобится запись с сохранением комментариев —
это делает крейт `toml_edit` (тот же, что использует cargo). Брать его сейчас
незачем: писать пока нечего.

### Р-014 · 2026-08-15 · Слежение за файлами опросом, без `notify`

Правка темы должна применяться на лету. Крейт `notify` для этого не берём

### Р-016 · 2026-08-15 · Свой заголовок окна

Системный заголовок отвергнут в пользу собственного, как в VS Code. Причина —

### Р-018 · 2026-08-15 · Смешанные переносы строк — решение пользователя

Внутри буфера все переносы одинаковы (`\n`): этого требует CodeMirror, который
хранит строки без завершителей и склеивает их одним разделителем. Значит для
файла со смешанными переносами не существует способа записать его обратно
байт в байт после правки.

Молча привести такой файл к преобладающему типу — прямое нарушение инварианта 1:
это нормализация без явной команды, причём затрагивающая каждую строку файла.

Принято:

* факт смешения определяется точно, с подсчётом каждого типа;
* он виден снаружи (`EolInfo.mixed`) и показывается в строке состояния;
* функция записи **требует явно указать** тип переноса — взять его «по
  умолчанию из файла» нельзя, потому что умолчания нет;
* нетронутый буфер не сохраняется вовсе, поэтому просто открыть и закрыть
  такой файл безопасно.

**Поведение интерфейса (уточнено 2026-08-15, задача 4).** При первом сохранении
изменённого файла со смешанными переносами показывается вопрос, к какому типу
привести, и файл приводится к выбранному целиком.

Рассматривался вариант сохранять исходный перенос у нетронутых строк — он точнее,
но требует держать исходные байты до первой правки и сопоставлять строки по
позициям. Отвергнут владельцем как несоразмерный: смешанные файлы в его работе —
крайняя редкость. Если у тестировщиков окажется иначе, вариант вернётся в план.

### Р-019 · 2026-08-15 · UTF-16 без метки определяется по старшим байтам

Наивная проверка «много нулевых байтов через один» ловит только латиницу.
Кириллица в UTF-16LE — это байты вида `21 04`, оба меньше `0x80`, нулей там нет
вовсе. Такой файл проходил проверку «весь в пределах ASCII» и объявлялся UTF-8,
превращаясь в кашу из управляющих символов. Дефект найден тестом при написании,
до того как попал куда-либо ещё.

Проверяется другое: байты одной чётности почти все меньше `0x08` (это старшие
байты кодовых единиц для латиницы, кириллицы, греческого, иврита, арабского),
а байты другой чётности разнообразны. Проверка идёт **до** всех остальных.

Ограничение, принятое сознательно: файл в UTF-16 без метки, состоящий в основном
из иероглифов или эмодзи, так не опознается. Такие файлы практически всегда идут
с меткой, а без неё кодировку можно выбрать вручную.

### Р-020 · 2026-08-15 · Непереводимый символ — ошибка до записи

Если в тексте есть символ, которого нет в кодировке файла (русское слово в файле
windows-1252), запись отвергается с указанием конкретного символа. Заменять его
на вопросительный знак, как делают многие редакторы, нельзя: это порча чужого
файла, о которой пользователь узнаёт слишком поздно.

Симметрично при чтении: если в байтах есть недопустимые для кодировки
последовательности, документ помечается `lossy`, и об этом надо сообщить до
сохранения — обратная запись байт в байт уже невозможна.

### Р-021 · 2026-08-15 · Эталоны лежат в репозитории и создаются генератором

`src-tauri/tests/fixtures/` содержит 17 настоящих файлов: все кодировки, обе

### Р-022 · 2026-08-15 · Свой формат проекта вместо повторения хранилища Obsidian

Изначальный замысел — «хранилище Obsidian открывается как проект» — предполагал,
что мы разбираем содержимое `.obsidian` и ведём себя как Obsidian. От этого
отказываемся.

**Почему.** Формат `.obsidian` не документирован и меняется от версии к версии.
Совместимость с закрытым чужим форматом — обязательство без дна: каждое их
обновление превращается в поток отчётов от тестировщиков. Кроме того, это
противоречит заявленной модели: ZeroNote сделан по образцу VS Code, а VS Code
не реализует чужие форматы проектов.

**Что вместо.** Разделение на три части:

1. **Проект — целиком наш.** Файл `zeronote.toml` в корне папки: правила
   игнорирования, настройки индексации, настройки редактора на проект. TOML,
   правится руками, кладётся в git — та же философия, что у `settings.toml`
   и тем.
2. **Чтение `.obsidian` сжимается до узкого переходника.** Один раз, при
   добавлении корня: опознать хранилище и перенести в **наш** файл проекта
   те два-три факта, которые нам действительно нужны (фильтры игнорирования,
   папка вложений). Односторонне, обратно не синхронизируется, результат
   пользователь правит руками. Если Obsidian поменяет формат, ломается
   переходник, а не работа с проектами.
3. **`[[wikilinks]]`, frontmatter и теги — свойство markdown-файлов в проекте
   ZeroNote**, а не «режима Obsidian». Правила разрешения ссылок наши и
   описываются здесь же. Они совпадают с обычным поведением Obsidian потому,
   что это здравое поведение, а не потому, что мы обязаны совпадать.

**Чего эта развязка не должна стоить.** Отличие ZeroNote от «Notepad++ с деревом
папок» держится на том, что он понимает связи между заметками. Если открыть
хранилище просто как папку с `.md`, первое, обо что споткнётся пользователь, —
`[[Заметка]]`, по которой некуда перейти. Поэтому пункт 3 обязателен, и отложить
можно его срок, но не сам факт.

Признак `Root.is_vault` из модели убран: он был подпоркой под «режим Obsidian»,
которого больше нет. Реализация — этап 2; на этап 1 решение не влияет.

### Р-023 · 2026-08-15 · Один редактор на окно, состояния подменяются

CodeMirror создаётся один раз, при переключении вкладки ему подставляется
другой `EditorState`. По представлению на вкладку было бы проще, но десяток
открытых файлов означал бы десяток живых представлений со своими обработчиками
и измерениями разметки.

Подмена ничего не теряет: текст, курсоры, прокрутка и история отмены входят
в `EditorState`, а не в представление. Порядок при переключении обязателен —
сначала сохранить состояние уходящей вкладки, потом поставить приходящую.

### Р-024 · 2026-08-15 · Признак изменения — сравнение с исходным текстом

Вкладка помечается изменённой не «была ли хоть одна правка», а сравнением
текущего документа с тем, каким он был при открытии или последнем сохранении.
Так откат всех правок через отмену снимает звёздочку, а не оставляет её висеть
навсегда.

Исходные тексты лежат в обычной `Map` вне реактивного состояния: интерфейсу
они не нужны, а держать их в рунах значило бы гонять лишние пересчёты на
каждое нажатие клавиши. Ядру сообщается только переход «чистый ↔ изменённый».

### Р-025 · 2026-08-15 · Перенос вкладок: порог и расчёт по соседям

Первая реализация переставляла вкладку от **обычного щелчка**. Две причины,
обе поучительные:

1. Не было порога начала перетаскивания. Мышь всегда сдвигается на пиксель-другой
   при нажатии, и этого хватало.
2. Место назначения искалось как «над какой вкладкой курсор». Этот способ ломается
   на самой перетаскиваемой вкладке: стоит курсору оказаться правее её середины,
   как он указывает на следующее место.

Стало: порог в 5 пикселей; место считается как «пересёк ли курсор середину
**соседней** вкладки», шаг всегда на одну позицию. Плюс защита от подвисшего
состояния — перетаскивания не бывает, если кнопка мыши не нажата (`buttons === 0`).
Без неё сорванный захват указателя превращал следующее же движение мыши в перенос.

Расчёт вынесен из компонента в `src/ui/tab-drag.ts` и покрыт тестом: дефект
был именно в нём, и повторять его не хочется.

Порядок вкладок уходит в ядро один раз, когда вкладку отпустили, а не на каждый
шаг мыши.

### Р-026 · 2026-08-15 · Файлы из командной строки

Редактор запускают не только с ярлыка: «Открыть с помощью» из проводника,
перетаскивание файла на значок, вызов из консоли. Аргументы разбираются
в `cli.rs`; всё, что начинается с дефиса, и значения известных флагов
пропускаются, остальное считается путями и открывается при старте.

### Р-027 · 2026-08-15 · Свой модальный диалог вместо системного

Системный диалог Tauri умеет ровно два ответа. Нам нужно больше: «к какому типу
переносов привести файл» — это три варианта плюс отказ, «закрыть вкладку
с правками» — сохранить, не сохранять, отмена.

Обходиться двумя кнопками нельзя. В диалоге закрытия «отмена» тогда означала бы
«не сохранять», то есть тихую потерю правок нажатием привычной кнопки. Это
именно тот класс дефектов, ради которого написан инвариант 4.

Свой диалог заодно выглядит по теме приложения. Вопрос задаётся из обычного
кода в `actions/` — функция возвращает обещание, которое разрешается выбором
пользователя, — поэтому логика действий не размазывается по компонентам.

### Р-028 · 2026-08-15 · Обе операции смены кодировки — в строке состояния

Кодировка и тип переносов в строке состояния сделаны кнопками. По кодировке
открывается меню с двумя разделами, повторяющими Notepad++:

* **Интерпретировать как** — перечитать те же байты другой кодировкой. Лечит
  крякозябры, файл не меняется, буфер остаётся чистым. Если в буфере есть
  несохранённые правки, спрашиваем: перечитывание возьмёт байты с диска
  и правки потеряются.
* **Преобразовать в** — оставить текст, сменить кодировку записи. Буфер
  становится изменённым. Переводимость проверяется ядром **сразу**, а не при
  сохранении: узнать о непереводимом символе в момент записи поздно.

Метка порядка байтов вынесена отдельным переключателем, а не удвоением списка
кодировок: это независимое свойство файла.

### Р-029 · 2026-08-15 · Закрытие окна проходит через те же вопросы

Закрытие окна перехватывается и подтверждается вручную: иначе несохранённые
буферы исчезли бы вместе с процессом. Обходятся все вкладки по очереди тем же
кодом, что и закрытие одной; отказ на любой отменяет закрытие целиком.

Это временная мера до задачи 5: когда появятся черновики, потеря данных
перестанет зависеть от диалогов вовсе. Но убирать вопрос и тогда не нужно —
пользователь должен понимать, что уходит с несохранённым.

### Р-030 · 2026-08-16 · Снимок сессии и черновики — разные файлы и разные ритмы

`session.toml` — маленький снимок: какие вкладки открыты, в каком порядке, какая
активна, кодировка и переносы каждой, где курсор и прокрутка. Пишется почти сразу
при любом изменении состава вкладок.

`drafts/<id>.draft` — содержимое, по файлу на буфер. Пишется с задержкой около
двух секунд после последней правки и только для тех буферов, содержимое которых
с прошлого сброса менялось.

Класть содержимое в снимок было бы проще, но тогда правка одного символа в файле
на десять мегабайт переписывала бы десять мегабайт при каждом сбросе. Разные
размеры данных требуют разных ритмов записи.

Черновики пишутся **всегда в UTF-8**, независимо от кодировки буфера. Это наши
служебные файлы, а не файлы пользователя: перекодировать их в cp1251 значило бы
рисковать потерей символов там, где рисковать нечем. Целевая кодировка лежит
в снимке и применяется при настоящем сохранении.

Оба файла пишутся через атомарную замену: оборванная запись снимка означала бы,
что восстанавливать нечего, — ровно в тот момент, когда это важнее всего.

### Р-031 · 2026-08-16 · Номера буферов сквозные между запусками

Именами файлов черновиков служат номера буферов, поэтому при восстановлении
номера берутся из снимка, а не выдаются заново. В снимке хранятся и счётчики —
следующий номер буфера и следующий номер безымянного, — иначе новая вкладка
получила бы номер уже открытой и затёрла бы чужой черновик.

Восстановление дополнительно поднимает счётчик до максимального занятого номера:
испорченный снимок не должен приводить к столкновению.

### Р-032 · 2026-08-16 · Буфер из черновика считается изменённым до сохранения

Признак изменения обычно вычисляется сравнением с исходным текстом (Р-024).
Для буфера, поднятого из черновика, исходного текста мы не знаем: на диске лежит
одно, в черновике другое.

Такой буфер помечается изменённым до первого сохранения безусловно. Иначе,
стерев в нём всё, пользователь получил бы «чистую» вкладку и закрыл бы её без
вопросов, потеряв то, ради чего восстановление и делалось.

### Р-033 · 2026-08-16 · Проверка инварианта 4 — настоящим убийством процесса

Модульные тесты проверяют запись и чтение снимка и черновиков. Этого мало:
инвариант 4 — про поведение живого приложения, а не про сериализацию.

`bench/crash-test.ps1` открывает файл, дописывает в него через настоящий
интерфейс, заводит буфер без файла, ждёт сброса черновиков, убивает процесс
через `Stop-Process -Force` и запускает снова. Проверяется, что обе вкладки
вернулись с их содержимым и что файл на диске остался нетронутым.

Прогон 2026-08-16: инвариант выполнен. Восстановились обе вкладки, их порядок,
активная вкладка, положения курсоров и признак изменения.

### Р-034 · 2026-08-16 · Внешние изменения: четыре разных случая

Опрос при получении окном фокуса, без крейта `notify` (решение Р-014):
именно в этот момент пользователь мог что-то сделать с файлом в другой
программе, и именно тогда стоит спросить.

| Случай | Поведение |
|---|---|
| Файл изменён, буфер чист | Перечитываем молча. Терять нечего, а спрашивать о том, что не имеет последствий, — раздражать без пользы. |
| Файл изменён, буфер изменён | Спрашиваем: оставить свои правки или взять версию с диска. Оставили свои — состояние файла принимается как эталонное, иначе вопрос повторялся бы при каждом возврате в окно. |
| Файл исчез | Спрашиваем всегда: закрыть вкладку или оставить содержимое. Оставили — путь сохраняется, и по нему буфер запишется обратно. |
| Файл изменился между чтением и сохранением | Проверка прямо перед записью. Молча затирать чужую работу нельзя; пишем только после подтверждения. |

Вопросы задаются **по одному**: модальное окно у нас одно, и возврат в окно
с тремя изменившимися файлами не должен приводить к тому, что два вопроса
потеряются.

Расхождение при сохранении возвращается отдельным полем результата, а не
строкой ошибки: это вопрос к пользователю, а не сбой, и отличать одно от
другого надо надёжно, а не разбором текста сообщения.

Проверено вживую на всех четырёх случаях: чистый буфер перечитался молча,
грязный спросил, исчезнувший файл предложил выбор и после сохранения
воссоздался, гонка при сохранении дала вопрос — и «не сохранять» оставило
чужую работу на диске нетронутой.

### Р-035 · 2026-08-16 · Редактор следит за подменой состояния, а не только за вкладкой

Дефект, найденный при проверке задачи 6 и живший с задачи 4.
`EditorHost` пересоздавал состояние представления только при смене активной
вкладки. Но `tab.editor` подменяется и без смены вкладки: при перечитывании
файла с диска и при операции «интерпретировать как».

В результате модель обновлялась, ядро считало файл перечитанным, а на экране
оставался прежний текст — и следующее сохранение записало бы устаревшее
содержимое поверх нового. Тихая потеря чужой работы, то есть ровно то, чего
не должно быть.

Теперь эффект зависит и от самого объекта состояния, а сравнение идёт по
тождеству. Собственные правки пользователя проходят через тот же эффект, но
там `tab.editor` и есть текущее состояние представления, поэтому ничего не
происходит. Запись состояния уходящей вкладки обёрнута в `untrack`, чтобы
эффект не вызывал сам себя.

Урок общий: реактивный эффект должен зависеть от того, **что** показывает,
а не от того, **чьё** оно.

### Р-036 · 2026-08-17 · Сочетание определяется по коду клавиши, а не по букве

`event.key` зависит от раскладки: при русской раскладке клавиша D даёт «в»,
и Ctrl+D перестал бы работать ровно тогда, когда пользователь набирает русский
текст. Для редактора с русскоязычной аудиторией это не мелочь, а полная
неработоспособность половины сочетаний.

Клавиша берётся из `event.code` — положения на клавиатуре, как это делает
Windows с виртуальными кодами и как ведёт себя Notepad++.

**Запасной путь по `event.key` добавлен после того, как обнаружилось, что
`code` бывает пустым.** Так приходят события от экранных клавиатур, программ
переназначения, средств специальных возможностей и любого источника, который
не сообщает скан-код. Отказываться от сочетания в таких случаях нельзя.
Кириллическая буква через запасной путь не проходит намеренно: независимость
от раскладки не должна теряться при первой возможности.

Дефект нашёлся при проверке живьём — все горячие клавиши молчали, хотя
раскладка загружалась и обработчики были на месте.

### Р-037 · 2026-08-17 · Список команд задан в Rust, обработчики — во фронтенде

Тот же приём, что с токенами оформления. Канонический перечень команд лежит
в `keymap/mod.rs`: по нему проверяется файл пользователя и называются опечатки.
Обработчики живут во фронтенде. Тест `tests/keymap.test.ts` сверяет, что наборы
совпадают ровно.

Дополнительно приложение проверяет целостность **на запуске**: если сочетание
указывает на команду без обработчика или раскладка вышла пустой, это
показывается полосой предупреждений. Тест ловит расхождение при сборке,
а проверка на живом приложении — то, чего тест не видит, например
недособранный реестр из-за порядка загрузки модулей.

### Р-038 · 2026-08-17 · Операции со строками написаны своими руками

`@codemirror/commands` предлагает готовые `moveLineUp`, `deleteLine` и прочие,
но их поведение отличается от Notepad++ в мелочах — а мелочи здесь и есть суть
совместимости. Свои реализации в `src/editor/commands.ts` умещаются в полсотни
строк и делают ровно то, что ожидает человек с мышечной памятью.

Все операции работают со **всеми** выделениями сразу: множественные курсоры
включены, и команда, применяющаяся только к первому, выглядела бы поломкой.

### Р-039 · 2026-08-17 · Поиск: движок библиотечный, панель своя

Поиск в список этапа 1 не входил, но критерий приёмки — «работать целый день
вместо Notepad++» — без `Ctrl+F` не выполняется. Добавлен по решению владельца
перед сборкой.

**Движок — `@codemirror/search`.** Своя реализация означала бы курсор по
документу с учётом переносов, границ слов, регистра и регулярных выражений —
неделя работы ради того, что уже есть в подключённом редакторе. Крейт входит
в ту же связку, что `@codemirror/state` и `view`, новых транзитивных
зависимостей не приносит.

**Панель — своя.** Штатная панель CodeMirror несёт собственную разметку
с зашитыми размерами и цветами, то есть прошла бы мимо слоя токенов и не
переживала бы смену темы. `openSearchPanel` не вызывается вовсе; из библиотеки
берутся только состояние запроса, подсветка совпадений и переходы.

Счётчик «3 из 17» считается обходом документа и потому вынесен в отложенный
пересчёт: на файле в десять мегабайт обход на каждое нажатие клавиши заметен
на глаз. Сам поиск при этом мгновенный — подсветку и переходы делает CodeMirror
по своему индексу.

Незакрытая скобка в регулярном выражении — не ошибка, а «пользователь ещё
дописывает»: поле подсвечивается, счётчик говорит «выражение не разобрано»,
ничего не падает.

### Р-040 · 2026-08-17 · Оконные сочетания не перехватывают ввод в полях

Дефект, найденный при проверке поиска: `Ctrl+A` в строке поиска выделял весь
документ вместо содержимого поля. Оконный диспетчер стоит на этапе перехвата
и забирал сочетание раньше, чем до него добиралось поле.

Правило: если фокус в обычном поле ввода — в панели поиска или в диалоге, —
команды с префиксом `edit.` пропускаются и достаются полю. Это ровно те
команды, что означают в поле совсем другое: `Ctrl+A`, `Ctrl+Z`, `Ctrl+Y`,
`Ctrl+D`, `Ctrl+L`, `Ctrl+U`.

Область текста CodeMirror под это правило не подпадает: она устроена как
`contenteditable`, но команды правки в ней как раз и должны работать.

### Р-041 · 2026-08-17 · Запасная папка данных не совпадает с папкой установки

Обнаружено при первой настоящей установке из пакета — до этого расхождение
было невидимым.

Установщик NSIS в режиме «для текущего пользователя» кладёт приложение
в `%LOCALAPPDATA%\ZeroNote`, а не в `%LOCALAPPDATA%\Programs\ZeroNote`, как
предполагалось в Р-008. Ровно этот же путь был выбран запасной папкой данных.

Совпадение означало бы, что при недоступной папке рядом с exe данные пишутся
внутрь папки установки: их снёс бы деинсталлятор, а при переустановке они
смешались бы с файлами программы. Запасная папка перенесена
в `%LOCALAPPDATA%\ZeroNote-data`; тест `paths::tests::fallback_is_not_the_install_directory`
следит, чтобы они больше не сошлись.

Проверено на этой машине: деинсталлятор удаляет `zeronote.exe` и `uninstall.exe`,
но папку `data\` со всем содержимым оставляет — как и обещано в README.

### Р-042 · 2026-08-17 · Lezer вместо Tree-sitter для подсветки

Решение «Tree-sitter» из первоначального стека принималось **до** выбора
CodeMirror и с ним плохо сочетается. CodeMirror 6 построен на Lezer —
инкрементальном парсере того же автора, спроектированном именно под него.
Скрещивание двух инкрементальных парсеров означало бы мост между двумя моделями
дерева, пересчёт на каждое нажатие и перегон диапазонов подсветки через IPC.

Подсветка — та единственная тяжёлая работа, которую **правильно** держать не
в Rust: документ уже живёт во фронтенде (Р-002), и гонять диапазоны через
границу на каждый символ прямо противоречит цели «ввод не блокирует отрисовку».

Берём `@codemirror/lang-*`: markdown, JavaScript/TypeScript, Rust, Python, JSON,
HTML, CSS, C++, XML, YAML. Этого хватает разработчику, у которого заметки и код
лежат рядом.

Tree-sitter не отвергнут навсегда: он останется уместен, если понадобится
структурный разбор помимо цвета — свёртка по блокам, оглавление, переход
к определению. Это этап 3, и там он не будет конкурировать с Lezer за подсветку.

### Р-047 · 2026-08-17 · Цвета подсветки — токены темы

Иначе тема перестаёт быть темой: подсветка осталась бы прежней при смене
оформления, и светлая тема с тёмными цветами кода выглядела бы сломанной.

Добавляет к слою токенов примерно полтора десятка имён (`syntax-keyword`,
`syntax-string`, `syntax-comment`, `syntax-number`, `syntax-type`…). Сторож
зашитых величин распространяется на них так же, как на остальные.

### Р-048 · 2026-08-17 · Окно параметров — этап 3

В этап 2 не входит. Настройки правятся файлом и подхватываются на лету, чего
для работы достаточно. Окно потребует `toml_edit` (Р-013) и своей формы под
каждый ключ — это отдельная задача, и она не мешает ничему из этапа 2.

### Р-049 · 2026-08-17 · Добавление корня не пишет в папку пользователя ничего

`zeronote.toml` создаётся только явной командой «Создать файл проекта», и та
ещё переспрашивает. Без файла проекта корень работает на умолчаниях.

**Почему.** Папку открывают в том числе чтобы просто посмотреть, и она вполне
может оказаться чужим репозиторием. Файл, созданный без спроса, — это правка
чужого каталога, то есть прямое нарушение инварианта 1, причём в том месте,
где её труднее всего заметить: в чужом `git status`.

Проверяется тестом `project::adding_a_root_writes_nothing_into_the_folder` —
он сравнивает содержимое папки до и после, рекурсивно. Тест, который просто
смотрит на отсутствие `zeronote.toml`, поймал бы не всё.

### Р-050 · 2026-08-17 · Правила игнорирования — семантика `.gitignore`

Своей семантики не изобретаем: `.gitignore` знает каждый, кто пользуется git,
а вторая система шаблонов в том же окне — это гарантированная путаница.

Матчер берётся из крейта `ignore` (согласован в Р-043). Своими руками это
порядок применения правил, отрицания, привязка шаблона к каталогу и вложенные
`.gitignore` — четыре места, где ошибка даёт файл, видимый в дереве и
отсутствующий в поиске. Крейт тянет `globset`, `walkdir`, `crossbeam-deque`,
`regex-automata`, `memchr`, `same-file`; цена признана оправданной, тем более
что на задаче 10 оттуда же берётся обход дерева.

Порядок сложения правил обратен по значимости — чем позже, тем сильнее:
встроенный список (`.git`, `node_modules`, `target`, `dist`, `.obsidian`),
затем `.gitignore` проекта, затем правила из `zeronote.toml`. Поэтому строкой
`!node_modules/` пользователь может вернуть то, что скрыли умолчания; обратный
порядок такой возможности не оставлял бы.

`.obsidian` скрыта из дерева, но остаётся читаемой: переходник задачи 15 лезет
туда напрямую, а не через правила. Запись в неё запрещена инвариантом 2
и проверяется отдельно.

### Р-051 · 2026-08-17 · Корни в сессии — поле с умолчанием, версия формата прежняя

`read_session` отвергает файл чужой версии целиком. Подъём `SESSION_SCHEMA`
до 2 означал бы, что при обновлении у каждого тестировщика молча закрылись бы
все открытые вкладки вместе с несохранёнными черновиками — обмен несравнимо
хуже того, что он покупает. Новое поле с `#[serde(default)]` обходится без
этого, а старый файл читается как «корней нет».

Версию поднимаем тогда, когда меняется смысл существующего поля, а не когда
добавляется новое. Проверяется тестом `session_without_roots_still_opens`
на дословном файле от версии 0.1.0.

### Р-052 · 2026-08-17 · Недоступный корень остаётся в списке

Папка могла пропасть потому, что вынули флешку, отвалился сетевой диск или
не поднялся VPN. Выбросить корень из рабочего пространства — значит стереть
настройку пользователя из-за временной причины.

Такой корень помечается недоступным, показывается блёклым, и о нём говорится
полосой предупреждений — пустое дерево без объяснений выглядит как поломка.
Возвращение диска подхватывается перечитыванием корней при получении фокуса
окном, тогда же, когда сверяются открытые файлы (Р-014).

### Р-053 · 2026-08-17 · Ctrl+B и Ctrl+Shift+O — из VS Code, а не из Notepad++

Раскладка Notepad++ — требование совместимости (Р-011), но папки как проекта
в Notepad++ нет, и брать сочетания для неё неоткуда. Взяты привычные по
VS Code: `Ctrl+B` — боковая панель, `Ctrl+Shift+O` — открыть папку.

Осознанная цена: в Notepad++ `Ctrl+B` — переход к парной скобке. Этой команды
у нас нет и в первом круге не будет; появится — займёт другое сочетание,
а не отберёт это, потому что менять раскладку задним числом хуже, чем выбрать
её один раз. `Ctrl+K Ctrl+O` из VS Code не подходит: последовательностей
из двух аккордов раскладка не поддерживает.

### Р-054 · 2026-08-17 · Дерево не обходится целиком, а читается по папке

Раскрыли папку — прочитали её содержимое, и только его. Так устроен
обозреватель VS Code.

**Почему не фоновый обход всего дерева.** Полный обход хранилища на сто тысяч
файлов упирается в потолок при любой реализации: его можно сделать фоновым
и отменяемым, но нельзя сделать мгновенным. Чтение одной папки мгновенно
всегда. Инвариант 6 здесь выполняется не отменяемостью, а тем, что обходить
нечего.

Полный обход всё-таки понадобится — индексу на задаче 11. Это другой
потребитель с другими требованиями: ему нужны отменяемость и показ хода
работы, а дереву нужна мгновенность. Мерить их поэтому надо порознь.

**Ссылки и точки соединения не разворачиваем.** `проект\ссылка → проект` —
это петля, в которой обход остаётся навсегда. Ссылка показывается, помечается
и не раскрывается.

### Р-055 · 2026-08-17 · Одиночный щелчок открывает файл обычной вкладкой

Режим предварительного просмотра из VS Code — курсивная вкладка, которую
вытесняет следующий открытый файл, — не делаем. Это отдельное состояние вкладки,
которое протекает в закрытие, сохранение и восстановление сессии, ради экономии
одного нажатия.

### Р-056 · 2026-08-17 · Скрытое правилами не показывается совсем

Ни блёклым, ни под переключателем «показать скрытые». Такой переключатель —
это ветвление в дереве, в поиске и в индексе: три места, где «видно» и «найдено»
начинают расходиться. Если понадобится — это отдельная задача с продуманной
семантикой, а не флажок.

### Р-057 · 2026-08-17 · Вложенные `.gitignore` учитываются, порядок источников сохранён

Задача 9 учитывала только корневой `.gitignore`. В любом репозитории половина
правил лежит не в корне, поэтому дерево показывало бы то, чего не должно.

Матчер каждого `.gitignore` привязан к своей папке — у git шаблоны
отсчитываются от места, где лежит файл. Цепочка собирается один раз на чтение
папки, а не на каждую запись в ней: иначе на папке в десять тысяч файлов одни
и те же файлы читались бы десять тысяч раз.

Порядок из Р-050 при этом сохранён: встроенный список, затем цепочка
`.gitignore` снаружи внутрь, затем правила из `zeronote.toml`. Ради этого три
источника держатся раздельными матчерами — у слитого порядок задаётся при
сборке и переопределить его нечем.

### Р-058 · 2026-08-18 · Индекс лежит в папке данных приложения

`data\index.db`, рядом с настройками и черновиками, а не в папке проекта.
Прямое следствие Р-049: в чужие папки мы не пишем. Побочное следствие,
о котором стоит знать заранее, — индекс большого хранилища весит десятки
мегабайт и в портативном режиме едет вместе с приложением.

Хранить индекс в папке проекта было бы удобнее для переноса, но означало бы
служебный каталог в каждом чужом репозитории и обязательную строку в чужом
`.gitignore`. Это не наша папка.

### Р-059 · 2026-08-18 · Одна база на все корни

Не файл на корень. Поиск сразу по всем корням — один запрос, а не склейка
выдач с несопоставимыми рангами: `bm25` считает редкость слова по своей базе,
и объединять ранги из разных баз бессмысленно. Миграция и открытие — одно
место, удаление корня — `DELETE WHERE root_id`.

Замечание в коде задачи 9 про «файлы индекса по номеру корня» этим решением
отменяется.

### Р-060 · 2026-08-18 · Схема индекса не мигрируется, а перестраивается

Индекс целиком выводится из файлов на диске, то есть это кэш. При смене версии
схемы база сносится и индексация запускается заново. Писать миграции для кэша
значит содержать код, единственная польза которого — сэкономить одну фоновую
индексацию.

Из того же соображения: файл, который не удалось прочитать как базу (обрыв
записи, повреждение диска, чужой файл с нашим именем), не ошибка запуска,
а повод построить заново.

### Р-061 · 2026-08-18 · Что попадает в индекс

Предел размера — ключ `[index] max_file_size`, по умолчанию 2 МБ. Двоичные
файлы отсеиваются по содержимому: управляющий ноль в первых 8 КиБ, как у git.

Списка расширений нет намеренно. Его пришлось бы вечно дополнять, и он молча
терял бы чужие текстовые форматы — а «молча теряет» здесь означает «файл
существует, но не находится», то есть худший вид дефекта: незаметный.

### Р-062 · 2026-08-18 · Отмена индексации — номер поколения, а не флаг

Флага хватило бы, чтобы прервать текущее задание, но не чтобы выбросить те,
что уже стоят в очереди: пришлось бы вычерпывать канал руками. Задание помнит
номер поколения, с которым его поставили; отмена увеличивает счётчик, и все
задания прошлых поколений просто не берутся в работу.

Незаконченная партия при отмене не сохраняется. Недописанное состояние хуже
отсутствующего, потому что выглядит завершённым.

### Р-063 · 2026-08-18 · Переход к совпадению — поиском по файлу, а не по индексу

В индексе нет номеров строк, и заводить их не будем: они устаревают при первой
же правке файла снаружи, а показывать пользователю неверную строку хуже, чем
не показывать никакой.

Щелчок по результату открывает файл и запускает по нему обычный поиск этапа 1 —
тот же код, что за Ctrl+F. Файл на диске всегда свежее индекса, поэтому
попадание точнее, а совпадения подсвечиваются все сразу.

Ищется первое слово запроса, а не запрос целиком: несколько слов индекс ищет
как «и», они могут стоять в разных концах файла, и поиск фразы не нашёл бы
ничего.

### Р-064 · 2026-08-18 · Нечёткое совпадение — подпоследовательность с надбавками

Буквы запроса встречаются в имени по порядку, но не подряд: `edtr` находит
`EditorHost.svelte`. Надбавки — за начало слова, за совпадение подряд, за
начало имени; штрафы — за пропуски и за длину. Совпадение в имени файла ценнее
совпадения в пути: человек ищет файл, а не папку.

Строгое вхождение подстроки заставляло бы помнить точное имя, то есть отменяло
бы смысл быстрого открытия. Схемы уровня fzf дают лучший порядок на длинных
запросах, но объяснить их пользователю нельзя, а «почему этот файл выше того» —
вопрос, который задают.

**Сопоставляется путь внутри корня, а не абсолютный.** Это дефект, найденный
живой проверкой: корень вроде `C:\Users\пользователь\Desktop\Project\...`
содержит столько общих букв, что под него подходит почти любой запрос, — и в
выдачу попадали все файлы проекта разом. Закреплено тестом
`root_path_does_not_take_part_in_matching`.

### Р-065 · 2026-08-18 · Поиск идёт по всем корням сразу

Переключателя «искать только здесь» нет. Корней обычно один, и лишний
переключатель ради редкого случая — это постоянная плата за редкую пользу.
Имя корня показывается в строке результата, только когда корней больше одного.

### Р-066 · 2026-08-18 · Языки подсветки грузятся по требованию

Открыли `.md` — приехал разбор markdown, и только он. Иначе парсеры всех
языков попадают в стартовый пакет, а это прямой удар по холодному старту,
который сейчас 430 мс при цели 2000.

Подставляется язык через `Compartment`: состояние вкладки создаётся сразу
и работает, язык встаёт на место, когда доедет. Пересборка состояния целиком
стоила бы истории отмены и положения курсора.

Незнакомое расширение — обычный текст, а не догадка по содержимому: неверная
подсветка хуже отсутствующей, потому что врёт про структуру. Язык при этом
выбирается вручную в строке состояния, рядом с кодировкой и переносами, —
там уже живут ровно такие переключатели. Выбор хранится в сессии: он не должен
теряться при перезапуске.

### Р-067 · 2026-08-18 · Роли подсветки общие, а не по языкам

Токенов пятнадцать: `syntax-keyword`, `syntax-string`, `syntax-comment` и так
далее. Ролей, а не языков: «ключевое слово», а не «ключевое слово Rust».
Иначе автор темы обязан был бы знать пятнадцать языков вместо пятнадцати ролей,
а добавление языка требовало бы правки всех тем.

Пять ролей выражены через общую палитру, а не через свои цвета: обычный текст
в коде — это просто текст, знаки препинания тише его, ссылка — акцент.
В палитре тем добавилось восемь цветов, а не пятнадцать.

Стиль подсветки ссылается на CSS-переменные, а не на значения из темы.
Поэтому смена темы меняет цвета кода сама — без пересборки стиля и без
переоткрытия вкладок.

### Р-068 · 2026-08-19 · Frontmatter только читается, и только два ключа

Из всего frontmatter берутся `aliases` и `tags`. Остальное содержимое
не толкуется и не меняется никогда — это инвариант 1.

Своего разбора YAML не пишем и библиотеку не берём. YAML — большой язык
с якорями, многострочными блоками и вложенностью; поддерживать его целиком
ради двух ключей значило бы взять обязательство, которое ничего не покупает.
Читаются два ключа в двух обычных записях — списком и строкой через запятую, —
а всё непонятное пропускается молча.

Список под чужим ключом в наши не утекает: иначе `authors` со списком имён
превратился бы в псевдонимы заметки. Проверяется тестом.

### Р-069 · 2026-08-19 · Внутри кода нет ни ссылок, ни тегов

Иначе `#include` в блоке C++ становится тегом, `#fff` в CSS — тоже,
а `[[i]]` в примере на Rust — ссылкой на несуществующую заметку. Разбор
пропускает содержимое огороженных блоков и вставок в обратных кавычках.

Ограда закрывается только такой же или более длинной — как в markdown.
Маскировка вставок сохраняет длину в байтах: смещения ссылок нужны для
перехода, и сдвинуть их значило бы привести пользователя не туда.

### Р-070 · 2026-08-19 · Переход по ссылке — Ctrl+щелчок и F12

Простой щелчок оставлен установке курсора. Режима просмотра у нас нет,
текст всегда редактируется, и увести пользователя в другой файл при попытке
поставить курсор — худшее, что можно сделать.

Подчёркивание появляется только при нажатом Ctrl, ровно тогда, когда щелчок
и правда уведёт. Подчёркивать постоянно значило бы обещать переход по
обычному щелчку, которого не будет.

`F12` — «перейти к определению» в привычке любого, кто пользовался средой
разработки. Ссылка между заметками — то же движение.

Висячая ссылка показывается приглушённой с пунктиром и никуда не ведёт.
Не красным: в живом хранилище висячая ссылка — обычное дело, так помечают
то, что собираются написать. Создавать заметку по такой ссылке приложение
не предлагает — это запись в папку пользователя (Р-049); отдельная команда
с переспросом появится, если понадобится.

Ссылки разрешаются пачкой на видимую часть документа, а не по одной:
полсотни ссылок на экране — это полсотни пересечений границы IPC на каждую
прокрутку. Ответы запоминаются и забываются по окончании индексации: пока
она идёт, висячая ссылка могла стать рабочей.

### Р-071 · 2026-08-19 · Переносим только то, что влияет на поведение

Из `.obsidian` берутся фильтры исключения (`userIgnoreFilters`) — и всё.
`attachmentFolderPath`, `newLinkFormat`, `alwaysUpdateLinks`, `tabSize`
описывают то, чего у ZeroNote нет: вставку вложений, создание ссылок, режим
просмотра.

Перенести их «на будущее» значило бы завести в нашем формате ключи, которые
ничего не делают, то есть заглушки. Появится вставка вложений — переходник
научится папке вложений тогда же, а не заранее.

Переходник вышел узким, и Р-022 ровно этого и требовал: «перенести те два-три
факта, которые нам действительно нужны».

### Р-072 · 2026-08-19 · Переносим только при создании файла проекта

Если `zeronote.toml` уже есть, переходник его не трогает: показывает готовые
строки в новой вкладке, а вставляет их пользователь.

Дописать в TOML вторую таблицу `[ignore]` нельзя — это неверный файл.
Переписать целиком значило бы потерять комментарии пользователя, а этого
мы не делаем без `toml_edit` (Р-013).

### Р-073 · 2026-08-19 · Оформление Obsidian не переносим вовсе

Цвет акцента, шрифт и тема в Obsidian — свойство хранилища; у нас — свойство
приложения. Перенос сломал бы границу: открыв два хранилища, пользователь
получил бы два несовместимых требования к теме.

Логотип Obsidian в интерфейсе тоже не используем: чужой знак намекает
на родство, которого нет.
### Р-074 · 2026-09-03 · Референс адаптируется, а не копируется

Дизайн «Slate» — прототип в HTML, показывающий задуманный вид, а не образец
для переноса. Где он расходится с нашей моделью, побеждает модель. Три
расхождения решены так:

1. **Вкладки остаются документами.** В референсе «Граф» и «Настройки» —
   такие же вкладки, как файлы. У нас вкладка равна буферу, и на этом держатся
   сессия, черновики, вопрос при закрытии и восстановление после падения.
   Настройки открываются панелью, а не вкладкой: смешать документы и экраны
   в одном ряду значило бы завести два вида вкладок с разным поведением
   при закрытии — переделку модели ради внешнего сходства.
2. **Окно без внешнего поля.** Референс рисует окно с полем 20 px и тенью
   вокруг. На Windows это прозрачное окно: пропадает прилипание к краям,
   а в развёрнутом виде рамка вокруг выглядит чужеродно. Берём скругление
   и тени, поле не берём.
3. **Графа связей не будет** — Р-046 остаётся в силе.

### Р-075 · 2026-09-03 · Шрифты вшиваются в пакет

`IBM Plex Sans` и `JetBrains Mono` кладутся в приложение файлами, а не
подключаются с Google Fonts.

ZeroNote работает без сети. Ссылка на внешний шрифт означает, что у половины
пользователей он молча подменится системным, и вся метрика дизайна — отступы,
высоты строк, ширина панелей — поедет. Молчаливая подмена хуже явного отказа.

Цена — 400–600 КБ к установщику за нужные начертания. Приемлемо: установщик
и так вырос до 3,66 МБ, а шрифт — это то, что видно в каждом кадре.

Пустой запрос ищет файлы, `>` — команды, `#` — теги. Так делает VS Code,

### Р-077 · 2026-09-03 · Окно параметров — надстройка над файлом

Экран настроек читает и пишет `settings.toml`, а не заводит своё хранилище.

Отсюда следует то, ради чего в Р-013 откладывался `toml_edit`: запись должна

### Р-078 · 2026-09-03 · Акцент задаёт тема, а не общая константа

Референс задаёт один акцент `#7B8CFF` на все семь тем и три альтернативы
к нему. У нас так не выйдет: акцентом печатается текст — ссылки, `[[вики-ссылки]]`,
имя активной вкладки, — а не только заливаются плашки. На белом фоне «Бумаги»
`#7B8CFF` даёт 3,3:1, то есть ссылки читаются хуже обычного текста.

Поэтому акцент — такой же цвет палитры, как остальные, и каждая тема выбирает
свой: «Бумага» — тот же оттенок, но темнее; «Хвоя» — зелёный, чтобы ссылки
не спорили с синими именами функций; «Сепия» — холодная бирюза, потому что
на тёплой бумаге тёплый акцент сливается с цветом типов.

Кому нужен единый акцент — он задаётся одной строкой в `[palette]` любой темы.

### Р-079 · 2026-09-03 · Цвет текста поверх акцента выбирает тема

Референс печатает по акценту белым. При светлом акценте это 3:1 — на кнопке
«Открыть» надпись видно хуже, чем рамку вокруг неё. Поэтому в палитре есть
отдельный `fg-on-accent`, и в пяти темах из семи он тёмный.

Тест считает контраст надписи на акценте наравне с остальным текстом: это самое
частое место, где нарядное побеждает читаемое.

### Р-080 · 2026-09-03 · Внешнего поля нет, поэтому `--bg0` в светлых темах не берётся

В референсе `--bg0` — фон вокруг окна, под полем в 20 px, а панели стоят
на `--bg1`. Поля у нас не будет (Р-074), и роли сдвигаются: рабочая область
редактора — самый дальний слой, панели ближе к пользователю.

Для тёмных тем это совпадает: `--bg0` там самый тёмный, редактор на нём и живёт.
Для светлых — нет: `#e8eaef` «Бумаги» серее панелей, и редактор на нём выглядел
бы вдавленным листом внутри белой рамки. В светлых темах рабочая область самая
светлая, панели чуть темнее её. Отсюда правило: **в тёмной теме фоны идут
от тёмного к светлому, в светлой — наоборот**, и `bg-2` в обеих означает
«всплывающая поверхность», а не «третий по яркости».

### Р-081 · 2026-09-03 · Шрифты переменные, латиница и кириллица раздельно

Развитие Р-075. Оба семейства раздаются переменными шрифтами: один файл
покрывает всю ось веса. Значит, три начертания — это не три файла, и вместо
двенадцати файлов лежат четыре, 125 КБ вместо ожидавшихся 400–600 КБ.

Разделение латиницы и кириллицы по `unicode-range` оставлено как есть: браузер
грузит только то, что понадобилось для отрисовки. Интерфейс на русском
не разбирает латинский файл до первого латинского символа.

`font-display: block`, а не `swap`: файлы читаются с диска мгновенно, а `swap`
означал бы кадр системным шрифтом и прыжок разметки на глазах у пользователя.

### Р-082 · 2026-09-03 · Операторы, знаки препинания и заголовки — из общей палитры

Было восемь цветов кода в палитре, стало шесть: `syn-operator` и `syn-heading`
убраны, роли выражены через общий текст. Оператор — `fg-1`, знак препинания —
`fg-2` (тише оператора), заголовок markdown — `fg-0` плюс вес.

Причина не в экономии, а в том, что эти три роли не про язык. Оператор и скобка
есть в любом языке и ничего не означают сверх того, что они разделители;
заголовок в референсе отличается весом, а не цветом, и так он и читается.
Отдельные цвета заставляли автора темы подбирать восемь оттенков вместо шести,
причём два из них — вслепую.

Кому нужен цветной заголовок, тот пишет `[color] syntax-heading = "..."` —
слой семантических ролей ровно для этого и существует.

### Р-083 · 2026-09-03 · Три слоя фона, и подложка окна — один из них

Уточняет Р-080, где я решил, что `--bg0` референса нам не нужен вовсе. Это было
верно ровно до задачи 18: как только между панелями появился зазор в два
пикселя, у этого цвета нашёлся потребитель — сам зазор.

Слои от дальнего к ближнему:

| Роль | Что это | Где видно |
|---|---|---|
| `color-bg-canvas` | подложка окна | зазоры между панелями и по краям тела |
| `color-bg-surface` | панели | дерево, поиск, полоса значков, шапка, вкладки |
| `color-bg-raised` | рабочая область | редактор, диалоги, всплывающие меню |

Прототип разделяет панели только рамкой: они того же тона, что и окно за ними.
Так можно, когда окно лежит на поле в 20 px и само читается карточкой. Поля
у нас нет (Р-074), и без разницы в тоне «панели» превратились бы в области,
разделённые волосяными линиями.

Отсюда правка светлых палитр: `bg-0` в «Бумаге» и «Сепии» стал серым — тем
самым `#e8eaef` из референса, который в Р-080 я назвал ненужным. Порядок
яркости в светлой теме от этого не переворачивается: подложка по-прежнему
самая дальняя, просто в светлой теме дальнее темнее, а в тёмной светлее.

### Р-084 · 2026-09-03 · Кнопки окна остаются системной формы

Референс рисует справа в шапке три круга — знак из macOS, и в прототипе они

### Р-085 · 2026-09-03 · Вкладки на уровне окна, заголовка в шапке нет

Вкладки идут во всю ширину окна, над полосой значков и боковой панелью, а не

### Р-086 · 2026-09-03 · Углы окна остаются прямыми; скругление отложено

Отрицательный результат, записанный, чтобы его не переоткрывали. Р-074 обещал
взять из референса скругление окна — оказалось, что дёшево его не взять.

Проверено, а не предположено. `PrintWindow` для этого не годится: он снимает
окно, а не композицию рабочего стола, и углы на его снимке всегда прямые.
Поэтому снят участок экрана вокруг угла по границам из
`DWMWA_EXTENDED_FRAME_BOUNDS`, с захватом области за окном. Угол прямой.

Дальше опробован `DwmSetWindowAttribute` с `DWMWA_WINDOW_CORNER_PREFERENCE`
и значением `DWMWCP_ROUND`. Вызов возвращает `S_OK` — и не делает ничего:
у окна без системного обрамления (Р-016) нет той самой рамки, к которой
диспетчер окон применяет скругление. Успешный код возврата здесь ничего
не значит, и если бы я его не проверил, я бы решил, что виноват снимок.

Остаётся прозрачное окно со скруглением средствами CSS. Это другой режим
композиции: своя тень, свои особенности отрисовки под курсором и на границе
изменения размера — заметная работа с риском задеть то, что уже работает,
ради четырёх углов. Отложено; строка добавлена в раздел «Отложено».

Код эксперимента удалён вместе с зависимостью `Win32_Graphics_Dwm`:
неработающий `unsafe` в репозитории хуже, чем его отсутствие. На тот момент
в проекте оставался один `unsafe` — `ReplaceFileW` (Р-006); второй появился
на этапе 5 ради чтения буфера обмена (Р-109).

### Р-093 · 2026-09-03 · Необратимый вариант виден цветом, а Enter всегда безопасен

Свой модальный диалог написан ради того, чтобы «отмена» не означала «не
сохранять» (Р-027). Задача 23 доводит это до конца двумя правилами.

**Необратимый вариант помечается цветом опасности.** «Не сохранять»
и «Сохранить», стоящие рядом, различаются одним словом, и промах стоит ровно
тех данных, которые человек набирал. Признак `danger` есть у трёх вариантов:
не сохранять при закрытии, перечитать файл другой кодировкой, взять версию
с диска.

**Вариант по умолчанию всегда безопасный.** В диалоге перечитывания по Enter
раньше срабатывало именно перечитывание — то есть нажатая не глядя клавиша
стирала правки. Теперь по умолчанию отмена.

### Р-094 · 2026-09-03 · Полоса предупреждений скрывается по набору сообщений

У полосы появилась кнопка «скрыть», и скрывается не полоса, а конкретный набор

### Р-095 · 2026-09-03 · Появление диалога и меню — та самая «базовая» анимация

В «Отложено» записано, что анимационных эффектов сверх базовых переходов
не будет. Всплывающее окно, приподнимающееся на треть отступа за 90–160 мс,
считается базовым переходом, и вот почему: оно короче времени реакции
и отвечает на вопрос «откуда это взялось», а не развлекает. Диалог, возникающий
мгновенно поверх текста, читается как подмена экрана.

Смещение берётся из токена отступов, длительность и кривая — из токенов
движения. Зашитых величин в анимации нет, иначе она прошла бы мимо слоя
токенов.

### Р-091 · 2026-09-03 · Ctrl+D отдан мультикурсору — единственное расхождение с Notepad++

Раскладка Notepad++ у нас заявлена требованием совместимости, а не вкусовщиной
(раздел 8). Здесь она нарушена ровно в одном месте, и сознательно: `Ctrl+D`
добавляет курсор на следующее совпадение, как в VS Code, а дублирование строки
переехало на `Ctrl+Shift+D`.

Конфликт всплыл при разборе задачи, а не при планировании: в плане было
записано «Ctrl+D — следующее совпадение», и то, что это сочетание уже занято
дублированием, я не заметил. Выбор сделал владелец.

Расхождение стоит записать явно, потому что оно единственное: человек
с мышечной памятью Notepad++ нажмёт `Ctrl+D` и получит не копию строки,
а второй курсор. Переназначается одной строкой в `keymap.toml`.

### Р-092 · 2026-09-03 · Перенос строк — настройка, а не свойство вкладки

Перенос длинных строк общий для всего приложения и живёт в `settings.toml`
ключом `[editor] wrap`. Переключается кнопкой в строке состояния — там же, где
кодировка и тип переносов, — и строкой в окне параметров.

Своё значение на каждую вкладку выглядит заманчиво: markdown хочется читать
с переносом, код — без. Но тогда состояние уезжает в сессию, его надо
восстанавливать, показывать и объяснять, а вопрос «почему в этом файле иначе»
возникает каждый раз заново. Так делает Notepad++, и это верное умолчание;
если понадобится своё на файл — это отдельная задача с отдельным разговором.

Применяется через отсек CodeMirror и обычную транзакцию, а не пересозданием
состояний: пересоздание стёрло бы историю отмены во всех открытых файлах разом.

### Р-090 · 2026-09-03 · История недавнего — свой файл и только явные открытия

Список недавнего лежит в `data/recent.toml`, а не полем в снимке сессии.
То же рассуждение, что в Р-030 про черновики: у сессии и у истории разные
вопросы и разные жизни. Сессия отвечает «что было открыто», история —
«что открывали раньше»; закрыв все вкладки, пользователь очищает первое
и не должен терять второе.

В историю попадает только явное открытие файла — из палитры, из дерева,
из диалога, перетаскиванием. Восстановление сессии при запуске не попадает:
это не действие пользователя, и после каждого запуска список выглядел бы
одинаково, независимо от того, чем занимались.

Существование файлов при показе не проверяется. Проверка означала бы двадцать
обращений к диску на каждое открытие стартового экрана, а на отключённом
сетевом диске — двадцать зависаний. Файл, которого нет, честно сообщит об этом
при попытке открыть, тем же путём, что и всегда.

Сочетания на экране берутся из действующей раскладки, а не вписаны в разметку:
переназначив `Ctrl+O`, пользователь увидит здесь своё сочетание. Экран, который
врёт про горячие клавиши, хуже экрана без них.

### Р-089 · 2026-09-03 · Окно параметров пишет по одной настройке и проверяет итог

Отменяет ограничение Р-013 «приложение файл только читает»: с этой задачи
приложение в `settings.toml` пишет. Условие, при котором Р-013 разрешал запись,
выполнено — `toml_edit` сохраняет комментарии.

Три правила записи:

1. **По одной настройке, сразу.** Ни «применить», ни «отменить» нет: файл
   и есть состояние (Р-077), а кнопка «применить» над файлом, который правят
   руками, завела бы второе состояние — то, что в окне, и то, что на диске.
2. **Итог проверяется нашим же разбором до записи.** Правка может быть верной
   по TOML и неверной по смыслу: тема с несуществующим именем, размер шрифта
   строкой. Записать такое — сломать пользователю оформление руками окна
   параметров.
3. **Испорченный файл не переписывается вовсе.** Окно показывает умолчания,
   называет ошибку и не даёт править: мы не знаем, что человек не дописал,
   и запись затёрла бы это.

Отдельно про удаление ключа — «взять из темы» для шрифта. `toml_edit` держит
комментарий перед ключом как его собственное оформление, поэтому обычное
удаление уносит и комментарий. Комментарий писал человек, и стирать его
за него мы не будем: при удалении оформление переносится на следующий ключ,
а если удаляемый был последним — остаётся у предыдущего.

### Р-087 · 2026-09-03 · Выбранный тег уходит в панель, а не разворачивается в палитре

Палитра в режиме `#` показывает теги, а не файлы: тег — это способ сузить
поиск, а не сам ответ. Выбор тега открывает панель поиска с готовым списком
помеченных файлов.

Разворачивать файлы прямо в палитре значило бы завести второй уровень внутри
всплывающего окна: выбрал тег — список сменился, нажал Escape — и непонятно,
закрылась палитра или вернулись теги. Панель же умеет то, чего палитра
не умеет никогда: остаться открытой рядом с файлом, пережить перезапуск,
показать отрывок.

Побочная выгода: поиск по тегу в панели написан ещё в задаче 12, и палитра
только зовёт его.

  дописывается звёздочка.

### Р-118 · 2026-09-04 · Сеть появляется только по нажатию и только с подписью

Решение владельца: обновление из GitHub делаем, и делаем **проверкой
и установкой по кнопке**.

Это первая сетевая функция за пять этапов. До сих пор «только локальная
файловая система» было не ограничением, а свойством: приложение не открывало
ни одного соединения, и об этом можно было говорить прямо. Теперь оговорка
появляется, и границы у неё жёсткие:

* **соединение — только по явному нажатию.** Ни фоновой проверки при старте,
  ни расписания. Нажали «проверить обновления» — сходили;
* **подпись обязательна.** У механизма обновлений Tauri своя пара ключей,
  и это **не** тот сертификат, которого у нас нет по Р-007. Открытый ключ
  вшивается в приложение, закрытый хранится у владельца и в репозиторий
  не попадает никогда. Не проходит проверка подписи — обновление
  отвергается, и об этом говорится словами;
* **ничего, кроме версии, наружу не уходит.** Ни счётчиков, ни отчётов,
  ни идентификаторов. Запрос к GitHub — это чтение одного файла;
* **скачанное ставится только по второму нажатию.** Между «нашлась новая
  версия» и «ставим» стоит человек.

Цена, которую надо знать заранее: **потеря закрытого ключа означает, что
установленные копии больше не обновятся никогда**. Ключ надо сохранить
отдельно от машины разработки — это не совет, а условие работоспособности
механизма.

### Р-119 · 2026-09-04 · Версию среды спрашиваем у системы, а не у строки агента

Окно рисует не наш код, а рантайм WebView2, установленный в системе: он
обновляется сам по себе, и жалоба «у меня не видно стрелки табуляции» без его
номера не воспроизводится. Поэтому в сведениях о программе он есть.

Первая версия задачи брала его из `navigator.userAgent` — оттуда, где он
и лежит на виду. В живом приложении вышло **`WebView2 152.0.0.0`**, а на той же
машине стоит **152.0.4191.62**: Edge с некоторых пор сокращает строку агента,
оставляя старший номер и нули вместо остальных.

Строка агента при этом не врёт — она ровно это и содержит. Врал бы наш вывод:
`152.0.0.0` выглядит точным номером, и в отчёте об ошибке его читали бы как
точный. Поэтому версия спрашивается у системы через `tauri::webview_version()`
(внутри — `GetAvailableCoreWebView2BrowserVersionString`), а разбор строки
агента убран совсем: запасной путь, который тихо даёт неверный ответ, хуже
отсутствия ответа.

Общее правило, ради которого это записано: **в сведениях о программе каждая
строка обязана быть проверяемой**. Их называют в переписке, по ним ищут
причину, и приблизительное число здесь дороже пропущенного.

### Что вышло в задаче 40

**Версия живёт в двух местах, и оба — не стартовый экран.** До этой задачи
номер показывался единственный раз — на стартовом экране, который исчезает
с первым же открытым файлом. Теперь он есть в окне параметров карточкой
и в палитре командой.

**Карточка стоит снаружи проверки на разобранный файл.** Всё окно параметров
живёт внутри `{#if values}` — без разобранного `settings.toml` показывать
нечего. Но на вопрос «какая у вас версия» отвечать надо и тогда, когда файл
испорчен: иначе версия прячется ровно в том случае, когда её и спрашивают.
Проверено на живом приложении с намеренно сломанным файлом.

**Подпись команды начинается со слова «Версия».** Спрашивают всегда версию,
а не «о программе», и в палитре ищут по тому слову, которое в голове.
Отсюда «Версия и сведения о программе»: находится и по «верс», и по «программ».

**Сочетания у команды нет и не будет.** В VS Code у «About» его тоже нет,
а место в раскладке дорого — и задача 41 как раз про то, что занятого места
уже больше, чем свободного.

**Своего окна у сведений нет** — это тот же модальный вопрос, что и все
остальные, с кнопками «Скопировать» и «Закрыть». Отдельное окно ради двух
строк текста означало бы второе место, где надо помнить про темы, фокус
и Escape.

**Ссылки на страницу выпусков в задаче нет** — по решению владельца она
отложена до задачи 44. Репозитория пока не существует, и адрес пришлось бы

### Р-120 · 2026-09-04 · `Ctrl+L` и `Ctrl+U` отданы эталону

Решение владельца по обоим.

`Ctrl+L` у нас удалял строку — сочетание Notepad++. В VS Code он её выделяет,
а удаляет `Ctrl+Shift+K`. Это единственное расхождение во всём списке, которое
**молча портит текст**: рука из VS Code жмёт `Ctrl+L`, ожидая выделения,
и получает удалённую строку. Прочие расхождения в худшем случае делают
не то, что ждали, но ничего не теряют.

Удаление никуда не делось: `Ctrl+Shift+K` — сочетание VS Code, и оно, как
выяснилось при разборе, работало и раньше, приходя из набора CodeMirror.
Теперь оно записано в раскладку, то есть видно в палитре и переназначаемо.
Цена решения: рука из Notepad++ получит на `Ctrl+L` выделенную строку вместо
удалённой. Заметно и безвредно.

`Ctrl+U` у нас переводил в нижний регистр. В VS Code и в самом CodeMirror это
«отменить последний курсор» — и эта команда у нас была, просто наше сочетание
её перекрывало. Мы отняли работающее и совпадающее с эталоном ради того, чего
в эталоне нет вовсе: сочетания для смены регистра в VS Code не существует.
Поэтому `Ctrl+U` возвращён отмене курсора, `Ctrl+Shift+U` освобождён заодно,
чтобы пара не разъехалась, а смена регистра осталась командой в палитре
и в контекстном меню.

### Р-121 · 2026-09-04 · Клавиша называется по положению, включая знаки препинания

В словаре сочетаний была ровно одна клавиша со знаком — `comma`, заведённая
под `Ctrl+«,»`. Всё остальное разбор нажатия не распознавал и возвращал «это
не сочетание».

Из этого следовало больше, чем казалось. Половину сочетаний VS Code нельзя
было ни назначить, ни отнять у редактора: `Ctrl+/`, `Ctrl+[`, `Ctrl+]`,
`Ctrl+Shift+\` до диспетчера просто не доходили. И там же нашёлся тихий
дефект: в списке сочетаний, отбираемых у вебвью, стояли строки `ctrl+=`
и `ctrl+-`, которых разбор не выдаёт никогда — он называет клавишу по
положению, а не по знаку. Совпасть эти строки не могли, и масштаб интерфейса
менялся на `Ctrl+«+»` вопреки написанному в коде. Написано было правильно,
проверить было нечем.

Теперь в словаре весь латинский набор знаков препинания, и назван он
по положению клавиши: `slash`, `bracketleft`, `equal`. Так же, как буквы
берутся из `code`, а не из `key`: сочетание не должно зависеть от того,
какая раскладка включена. Это же понадобится редактору клавиш в задаче 42 —
он обязан уметь записать то, что человек нажал.

### Р-122 · 2026-09-04 · Сочетания редактора остаются за редактором

Разбор начался с проверки очевидного и сразу нашёл неочевидное: в окне
работает не только наша раскладка. CodeMirror ставит свой набор
`defaultKeymap`, и десяток сочетаний нажимается мимо реестра — включая те,
которых мы «не имеем»: `Alt+↑` двигает строку, `Shift+Alt+↓` дублирует,
`Ctrl+Shift+K` удаляет, `Ctrl+/` комментирует. Проверено нажатиями
в отладочной сборке, а не выведено из документации.

Наш диспетчер стоит на этапе перехвата и глушит событие, поэтому наше
сочетание всегда сильнее. Всё, чего в реестре нет, достаётся редактору.

Забирать их все в реестр мы не будем. Это примитивы правки и движения
курсора — выделение по разбору языка, отступ, сведение курсоров, — и, забрав
имя, пришлось бы отвечать и за поведение: у нас уже есть пара, где своя
реализация беднее чужой (см. раздел 8, перемещение строк). Взято только то,
у чего в реестре появляется собственный смысл: выделение строки, отмена
курсора, комментирование — четыре команды, которые до сих пор работали,
но не показывались ни в палитре, ни в меню и не переназначались.

Остальное записано списком в разделе 8. Молчаливо работающее сочетание —
это не удобство, а то, о чём нельзя рассказать пользователю.

### Р-123 · 2026-09-04 · Аккордов не будет

Решение владельца. `Ctrl+K Ctrl+0` — не сочетание, а последовательность,
и стоит она дороже, чем выглядит: состояние «ждём вторую клавишу», срок
ожидания, подсказка о том, что мы его ждём, новый вид подписи в меню
и в палитре, изменение схемы `keymap.toml` и захват двух нажатий в редакторе
клавиш из задачи 42.

Всё это ради двух-трёх сочетаний свёртки, у которых уже есть свои — из
Notepad++, и они короче. Строка в «Отложено».

Решать надо было именно сейчас, до задачи 42: редактор клавиш, написанный
под одно нажатие, переделывается под два не бесплатно.

### Что вышло в задаче 41

**Разбор нашёл больше, чем искал.** План говорил о шести расхождениях
с VS Code. Их оказалось одиннадцать, но пять из них разошлись только на
бумаге: сочетание VS Code работало и раньше — просто приходило из чужого
набора и потому не было видно ни в палитре, ни в меню, ни в файле раскладки.

**Четыре команды перестали быть невидимыми**: выделить строку, отменить

незачем — взяты именами в реестр, чтобы у них были подпись, место в палитре
и возможность переназначения.

**Один тихий дефект найден заодно** — `ctrl+=` и `ctrl+-` в списке отбираемых
у вебвью не совпадали ни с чем (Р-121). Код был написан правильно, а проверить
его было нечем: сочетание, которое никогда не срабатывает, выглядит точно так
же, как сочетание, которое не понадобилось.

### Чего в этапе нет

**Непрерывной сборки.** Открытый репозиторий обычно проверяется сборкой

**Автосохранения.** Владелец собирался посмотреть, будет ли рука тянуться
к `Ctrl+S`. Вопрос остаётся открытым, задачи пока нет.

### Р-106 · 2026-09-03 · Отступ определяется по файлу, а настройка — только умолчание

Задача 35 упирается в инвариант 1 сильнее, чем кажется. Настройка «отступ —
два пробела», применённая к чужому файлу с табами, означает, что первое же
нажатие `Tab` смешает в нём одно с другим. Файл станет другим не от команды
пользователя, а от того, что у нас в конфиге.

Поэтому: для существующего файла отступ **определяется по его содержимому** —
что в нём преобладает, тем и продолжаем. Настройка задаёт умолчание для новых
файлов и для тех, где определить не удалось. Показывать определённое надо
в строке состояния: молчаливая догадка хуже настройки.

Это то же правило, по которому уже живут кодировка и перенос строк: файл
диктует, настройка подсказывает.

### Р-107 · 2026-09-03 · Пункт меню не заводит своё действие

Контекстное меню — третий способ вызвать то же самое, после клавиш и палитры.
Пункт меню ссылается на команду из реестра `keymap/`, а не повторяет её тело,
и сочетание в подписи берёт оттуда же.

Иначе получится ровно то, что уже случалось с сочетаниями до этапа 3: подпись
в интерфейсе и настоящее нажатие разъезжаются, и заметить это можно только
глазами. Канонический список — в реестре, потребитель — меню; это тот же
приём, что у токенов и раскладки.

### Р-108 · 2026-09-03 · Буфер обмена на своих клавишах остаётся за вебвью

Р-107 требует, чтобы пункт меню ссылался на команду реестра. Для «вырезать»,
«копировать» и «вставить» это значило бы перехватить `Ctrl+X`, `Ctrl+C`
и `Ctrl+V` — и заменить рабочий путь своим подражанием.

Подражание вышло бы хуже. Копирование в CodeMirror умеет неочевидное: при
пустом выделении берёт целые строки, при вставке раздаёт строки по курсорам,
а построчно скопированное вставляет перед строкой, а не в середину слова.
Всё это работает и проверено годами чужой эксплуатации.

Поэтому команды в реестре есть, сочетания за ними записаны — но нажатие
на **своей** клавише уходит мимо нас, к вебвью. Сверяется пара «команда —
сочетание»: переназначил пользователь копирование на другую клавишу — её
выполняем мы, и подпись в меню покажет её же; занял `Ctrl+C` чем-то своим —
копирования на нём больше нет, и меню об этом честно промолчит.

Своя реализация всё равно понадобилась — для пунктов меню, палитры и
переназначенных сочетаний. Она написана по исходникам CodeMirror и держится
тестами (`tests/clipboard.test.ts`): пункт меню и клавиша называются
одинаково и обязаны делать одно и то же.

Второе следствие того же правила — **контекстные пункты**. «Закрыть другие»,
«копировать путь», «показать в проводнике» действуют на то, по чему щёлкнули,
и команды реестра у них нет и быть не может: у клавиши нет объекта под
курсором. Такие пункты живут только в меню, и это видно по имени —
`menu.copy-path`, а не `file.copy-path`.

Отсюда же правило для вкладок: **правый щелчок сначала делает вкладку
активной**. Иначе «Сохранить» из меню третьей вкладки сохранило бы первую.
Так же ведёт себя Notepad++.

### Р-109 · 2026-09-03 · Буфер обмена читается ядром, потому что браузером не читается

`navigator.clipboard.readText()` в нашем WebView2 **не отвечает вовсе**:
обещание не разрешается и не отвергается. Это измерено в живом окне, а не
предположено, — и это худший вид отказа. Ветка ошибки никогда не сработает,
сообщения не будет, пункт «Вставить» просто молча не делает ничего.
Первая реализация была именно такой, и её отличие от рабочей нельзя было
увидеть глазами.

Чтение переехало в ядро, запись осталась браузерной: `writeText` работает
(им же сделана кнопка копирования блока кода в задаче 28), и гонять её через
ядро незачем.

Нового крейта не понадобилось. `windows-sys` в проекте уже есть — ради
`ReplaceFileW` (Р-006); ему добавлены два раздела, и чтение буфера обмена
заняло пять системных вызовов. Взять ради них `arboard` или
`tauri-plugin-clipboard-manager` значило бы притащить поддержку картинок,
записи и трёх операционных систем ради одной функции: библиотека решала бы
не малую часть задачи, а всю, но и её саму заменяет полстраницы кода.

Цена — **второй `unsafe` в проекте** (первый — `ReplaceFileW`). Он собран
в одном месте, `src-tauri/src/clipboard.rs`, и разобран по строкам в
комментарии: чей указатель, кто владеет памятью, чем ограничено чтение
до нуля. Чужая память не освобождается, длина ограничена настоящим размером
блока, непарный суррогат не роняет разбор.

Захват буфера обмена делается с несколькими попытками: он один на всю
систему, и отказ — обычное дело, а не сбой. Одна попытка означала бы
«иногда вставка не работает», и объяснить это было бы нечем.

### Р-110 · 2026-09-03 · Удаление есть, но только в корзину

Решение владельца по вопросу, оставленному в плане: дерево получает создание,
переименование и удаление. Удаление — **только в корзину, и никогда мимо неё**.

Р-049 это допускает: пункт меню и есть та самая явная команда. Но у удаления
две особенности, которые надо учесть при исполнении, а не обнаружить потом.

**Первая.** `SHFileOperationW` с флагом «в корзину» удаляет мимо корзины
молча — когда корзины нет вовсе (сетевой диск, съёмный носитель) или когда
файл в неё не помещается. Тогда правильный ответ не «удалить насовсем»,
а отказ с объяснением: пользователь выбрал корзину, а не удаление.

**Вторая.** Отказать надо и там, где удалять нельзя по нашим же правилам:
внутри `.obsidian` (инвариант 2), на самом корне (для него есть «Убрать
папку») и на всём, что лежит вне корней.

Спрашивать перед удалением — своим диалогом, где безопасный вариант
по умолчанию, а необратимый помечен цветом (Р-093).

Переименование и создание отдельного решения не требуют: ошибка в них
обратима, а проверки те же, что у создания заметки по ссылке (Р-104) —
запретные знаки в имени, `..`, выход за корень, существующий файл.

### Р-111 · 2026-09-03 · Alt с дополнительной клавиатурой — не сочетание

`Alt+0151` даёт тире, `Alt+0171` — открывающую кавычку. Пишущий по-русски
набирает так каждый день, и это не редкость, а обычный ввод. Свёртка при этом
висит на `Alt+0` — сочетании Notepad++.

Столкновение реальное: наш разбор нажатия приводил цифру дополнительной
клавиатуры к обычной (`Numpad0` → `0`), и первое же нажатие в наборе тире
свернуло бы весь файл вместо ввода знака.

Правило: **`Alt` с цифрой на дополнительной клавиатуре сочетанием не считается
вовсе.** Цифра верхнего ряда — считается. Windows эти клавиши различает
(`VK_0` против `VK_NUMPAD0`), Notepad++ тоже, и мы теперь тоже.

Проверено на живом окне: `Alt+0151` вставляет тире и ничего не сворачивает.

### Что вышло в задаче 33

Свёртка целиком приехала из разбора языка — своих правил вида «фигурная
скобка открывает блок» здесь нет ни одного. Такое правило пришлось бы писать
заново на каждый язык и всё равно врать на строках и комментариях, а дерево
разбора уже знает, где блок. Заголовки markdown сворачиваются до следующего
заголовка того же уровня — это тоже свойство разбора, и оно закреплено
тестом: библиотеку обновят, а поведение должно остаться.

Поле свёртки стоит справа от номеров строк, значок — тот же уголок, что
у папки в дереве, и поворачивается по тому же правилу. Заглушка на месте
свёрнутого перекрашена токенами: базовая тема CodeMirror задаёт ей цвета
числами, и в тёмной теме она светилась белым.

Подписи CodeMirror переведены через `EditorState.phrases` — иначе во
всплывающей подсказке посреди русского интерфейса стояло бы «unfold».

Чего свёртка не покрывает: языки из `legacy-modes` — TOML, YAML, INI, SQL,
Shell, PowerShell, Lua. Разбор там построчный, дерева нет, и сворачивать
нечего. Свёртка по отступам записана в «Отложено».

Заодно **меню закрывается от любой клавиши**, а не только от Escape. Пока
не закрывалось, `Alt+0` из-под открытого меню сворачивал файл, а меню
продолжало висеть поверх изменившегося текста и показывать состояние,
которого больше нет.

И главное по стенду: **`SendKeys` шлёт нажатия без скан-кода**. Скан-код —
то, из чего Chromium делает `event.code`, а на нём построена вся наша
раскладка (Р-036). Без него `Alt+Shift+0` приезжает как `)` и не совпадает
ни с чем, а `Ctrl+C` не превращается в команду копирования. Две проверки
подряд — вчерашняя про буфер обмена и сегодняшняя про свёртку — выглядели
как дефекты приложения; оба раза виноват был стенд. Теперь сочетания шлются
через `keys.ps1 -Chord` в том же виде, в каком они пишутся в `keymap.toml`.

### Р-112 · 2026-09-04 · Закрытие скобок берём из пакета автодополнения

`closeBrackets` в CodeMirror живёт в пакете `@codemirror/autocomplete` —
и это единственное, что из него берётся. Название пакета к делу отношения
не имеет: автодополнение включается отдельным вызовом, которого в проекте нет.

Своими руками это не пять строк, а обработчик ввода с оглядкой на
мультикурсор, обёртывание выделения, удаление пустой пары по `Backspace`
и поведение при отмене. Библиотека решает задачу целиком и делает это
годами в чужой эксплуатации.

Опасность здесь одна и она не техническая: «пакет уже в зависимостях» —
самый лёгкий путь к тому, чтобы автодополнение однажды в нём и включили.
Поэтому граница стережётся тестом `tests/brackets.test.ts`: из пакета
разрешено импортировать только `closeBrackets` и `closeBracketsKeymap`,
а вызова автодополнения не должно быть нигде.

### Р-113 · 2026-09-04 · В прозе кавычка сама не закрывается

Автозакрытие включено по умолчанию — этап про «каждый день», а закрывающая
скобка, приезжающая сама, есть везде, откуда к нам приходят: и в VS Code,
и в Obsidian. Выключается настройкой `[editor] auto_close`.

Но кавычка — не скобка. «Сказал» в русском тексте не начало строкового
литерала, и вторая кавычка, приехавшая сама, всегда лишняя. Поэтому:

* **проза** — markdown и текст без языка (`.txt`, новый буфер, незнакомое
  расширение) — закрывает `(`, `[`, `{` и не закрывает кавычки;
* **код** остаётся с умолчанием CodeMirror: там кавычка как раз парная.

Устроено это данными языка, а не своим обработчиком ввода: `closeBrackets`
спрашивает набор скобок у состояния, и первый ответ побеждает. Когда язык
есть, наше правило молчит — и порядок расширений перестаёт что-либо значить.

Заодно правило про переход к паре: **что подсвечено, к тому и переходим.**
Порядок поиска взят тот же, что у подсветки CodeMirror, включая случай
«курсор внутри только что набранной пары». Расхождение означало бы «пара
подсвечена, а перейти нельзя», и объяснить это было бы нечем.

### Р-114 · 2026-09-04 · Ориентир — VS Code и Obsidian, от Notepad++ остаётся скорость

Решение владельца, меняющее основание, на которое проект ссылался четыре
этапа. Раньше было записано: «раскладка Notepad++ — требование совместимости,
а не вкусовщина». Теперь эталон другой.

Формулировка владельца: от Notepad++ берём **скорость развёртывания** —
мгновенный старт, мгновенное открытие файла, работу без установки чего-либо
ещё. Всё остальное — удобства, оформление, сочетания — равняется на VS Code
и Obsidian, потому что Notepad++ по существу текстовый редактор, а ZeroNote
метит выше.

**Что это меняет сразу.** Умолчания, которых ещё не было, берутся из VS Code.
В этой самой задаче: отступ по умолчанию — четыре пробела, а не таб.

**Чего это не означает.** Занятые сочетания не переставляются задним числом
без нужды: у нас тридцать пять тестировщиков, работающих с приложением
четвёртый месяц, и внезапная смена клавиш обойдётся им дороже, чем нам —
несовпадение с эталоном. Расхождения разбираются отдельной задачей этапа 6,
списком и разом, а не по одному втихую.

**Что перестаёт быть исключением.** Р-053 (`Ctrl+B` и `Ctrl+Shift+O` из
VS Code) и Р-091 (`Ctrl+D` — мультикурсор) записывались как расхождения
с эталоном и уступки. Теперь это просто совпадение с новым ориентиром.

### Р-115 · 2026-09-04 · `Tab` остаётся за редактором, а не за реестром команд

Единственное сочетание, которое не проходит через реестр команд и не
переназначается в `keymap.toml`. Причина не в лени: `Tab` вне текста
означает совсем другое — переход по элементам интерфейса. Перехватив его
глобально, мы отняли бы клавиатурную навигацию у окна параметров, у диалогов
и у панели поиска.

До этой задачи `Tab` не был занят вовсе, и в редакторе он делал то, что
делает в браузере, — уводил фокус из текста. Для редактора это дефект,
просто никем не замеченный: `Tab` в нём нажимают не задумываясь.

Заодно правило, которое легко нарушить из лучших побуждений: **смена отступа
не переписывает файл.** Выбор в строке состояния меняет только то, чем
набирается новый отступ. Преобразование уже набранного — это правка всего
файла, и она может быть только отдельной явной командой, которой у нас пока
нет (инвариант 1).

### Что вышло в задаче 36

Пробелы и табы рисует CodeMirror, знак переноса — наш: в библиотеке его нет,
а без него не видно, где кончается строка с хвостовыми пробелами, то есть
половина смысла режима пропадает.

Оба цвета CodeMirror задаёт числами — точку серым `#aaa`, стрелку табуляции
картинкой с зашитым `#888`. Перекрыты токенами: точка — тем же градиентом,
но с переменной, стрелка — знаком вместо картинки, потому что цвет внутри
`data:`-URI переменной не задать.

**Перенос помечается одним знаком, а не «CRLF» и «LF».** Показать разные было
бы честно только при разных данных, а их нет: документ внутри всегда с `
`,
настоящий тип переноса живёт в модели буфера и применяется при записи
(инвариант 5). В файле со смешанными переносами все строки получили бы
одинаковую подпись — то есть враньё. Тип переноса показывает строка состояния,
и там он один на файл, каким и является.

**Переключателя в строке состояния нет, вопреки плану.** План писался до того,
как в строку добавились позиция курсора и отступ, и до Р-114. В VS Code строка
состояния показывает свойства файла — кодировку, перенос строк, язык, отступ,
положение курсора, — а переключатели вида «показывать невидимые» живут в меню
и в палитре. У нас ровно тот же набор свойств плюс один переключатель
(«перенос»), доставшийся от прежнего ориентира; двигать его теперь дороже,
чем не добавлять второй. Команда `view.invisibles` есть в палитре и в
контекстном меню редактора — с галочкой, потому что это состояние, а не
действие.

Заодно `edit.toggle-wrap` получила сочетание `Alt+Z` — как в VS Code. Раньше
команда была в реестре вовсе без сочетания.

### Р-116 · 2026-09-04 · Закладки живут в состоянии редактора

Не списком номеров строк сбоку, а `RangeSet` внутри `EditorState`. Разница
видна на первой же правке: вставили десять строк выше — закладка уехала
вместе со своей строкой, потому что `RangeSet` переносится через изменение
сам. Список сбоку пришлось бы поправлять руками на каждое изменение текста,
и первая же забытая правка сделала бы закладки бесполезными — причём
незаметно: метка осталась бы на номере, который теперь показывает другое.

Оттуда же бесплатно берётся переключение вкладок: `EditorState` у каждой
вкладки свой.

**В сессию уезжают номера строк, а не позиции.** Файл могли поправить
в другой программе, пока приложение было закрыто, и номер переживает такую
правку лучше, чем смещение в знаках. Номер за концом файла отбрасывается:
придумывать строку, которой нет, незачем.

Своего поля у номеров строк закладки не получили — помечается сама ячейка
с номером. Третье поле слева отняло бы место у текста ради того, что и так
видно.

### Что вышло в задаче 37

Дефект, найденный по дороге и родственный Р-105: **переключение закладки
не меняет ни текст, ни выделение**, а наш слушатель обновлений звал обработчик
только на эти два случая. Состояние вкладки оставалось прежним, и в сессию
уезжали вчерашние закладки. Нашлось при проверке сохранения — первая версия
писала в сессию пустой список и выглядела рабочей: на экране-то метки стояли.
Теперь у изменения закладок свой обработчик, и он же просит сохранить сессию.

**`F2` и задача 38.** Сочетания взяты из Notepad++: в VS Code закладок нет
вовсе, брать оттуда нечего, и Р-114 здесь молчит. Но `F2` в VS Code —
переименование, и в дереве файлов это сочетание ждут именно на нём. Задача 38
добавляет операции с файлами в дерево, и `F2` там придётся сделать
контекстным — как `Tab` (Р-115): в тексте закладка, в дереве переименование.
В самом VS Code `F2` тоже контекстный, так что расхождения с эталоном
не возникает. Диспетчер сочетаний это пока не умеет — в задаче 38 научится.

### Р-117 · 2026-09-04 · Клавиша может значить разное в разных местах

`F2` в тексте — переход к следующей закладке, `F2` в дереве — переименование.
Это не исключение из правила «все сочетания в реестре», а признание того,
что часть клавиш контекстна по своей природе: `Tab` уже такой (Р-115),
и в VS Code `F2` тоже — там он переименовывает и файл в дереве, и символ
в тексте, смотря где фокус.

Устроено списком в оконном диспетчере: команда — место, которому она уступает.
Пока в списке одна строка. Механизм намеренно скучный: селектор и `closest`,
а не система областей видимости с приоритетами. Второй такой случай появится
не скоро, а третьего может не быть вовсе.

**Цена, о которой надо знать.** `F2` в дереве работает, когда фокус в дереве, —
то есть после щелчка по папке или после прихода в дерево клавишами. Щелчок
по файлу открывает его и уводит фокус в редактор, и там `F2` снова про
закладки. В VS Code ровно так же (`filesExplorerFocus` в условии сочетания),
так что расхождения с эталоном нет, но пункт меню — путь, который работает
всегда.

### Что вышло в задаче 38

**Удаление только в корзину — две меры, и обе нужны.** `SHFileOperationW`
с флагом «в корзину» удаляет мимо корзины **молча**, когда корзины нет или
файл в неё не помещается: самый опасный случай выглядит как обычный успех.
Поэтому, во-первых, до удаления спрашивается `SHQueryRecycleBin` про том,
на котором лежит файл, — нет корзины, отказ с объяснением, ничего не тронуто.
Во-вторых, стоит флаг `FOF_WANTNUKEWARNING`: он частично отменяет «без
вопросов» и предупреждает ровно там, где система собралась удалить насовсем.
Вместимость корзины узнать заранее нечем, поэтому этот случай остаётся
за системой: она спросит, человек ответит. Молча не удалится ничего.

**Открытые вкладки переезжают вместе с файлом.** Не только сам файл:
переименовали папку — переехало всё, что внутри неё открыто. Без этого
сохранение любой такой вкладки создало бы файл по старому пути, то есть
копию, которую никто не просил. Ядро для этого получило `move_buffer`:
он меняет путь и имя вкладки и **не трогает** признак изменения — файл тот же
самый, несохранённые правки никуда не делись.

**Вкладки удалённого закрываются без вопроса.** Обычное закрытие спросило бы
«сохранить изменения перед закрытием?» — то есть предложило бы создать файл
заново, ровно то, от чего человек только что отказался.

Проверок имени пять, и три из них неочевидны: `CON` не создастся вовсе,
имя с точкой на конце создастся, но другое, а `..` увело бы на уровень выше.
Всё это чистые функции и тесты, а не проба на живой файловой системе.

**Найденный по дороге дефект интерфейса.** Кнопка диалога ввода была
подписана «Перейти» всегда — просто потому, что первым его позвал переход
к строке. В диалоге «новый файл» это читалось как ошибка. Теперь подпись
задаётся вызывающим и умолчания не имеет: «Перейти», «Создать»
и «Переименовать» — разные обещания.

### Идеи владельца на этап 6

Пришли по ходу этапа 5. Все вошли в план этапа 6 — раздел 20; здесь оставлен
разбор, из которого он вырос.

**Панель форматирования markdown** — жирный, курсив, выделение, заготовки.
Границ не задевает: это правка по явной команде, то есть то же самое, что
пользователь набрал бы руками. Ложится в тему «каждый день» лучше всего
из четырёх.

**Публикация в открытый доступ.** Лицензия MIT в репозитории уже лежит,
установщик собирается. Что проверить перед тем, как давать ссылку: в истории
и в файлах не должно остаться личных путей и данных владельца, а сборка
должна проходить из чистого клона на чужой машине. Разослать ссылку —
не то же самое, что положить репозиторий: тестировщиков тридцать пять,
и первое же их впечатление будет от README, а не от кода.

**Обновление из GitHub** — здесь нужно решение, а не задача. Это **первая
сетевая функция в проекте**: до сих пор приложение не открывало ни одного
соединения, и «только локальная файловая система» было не ограничением,
а свойством. Отдельно: механизм обновлений Tauri требует **своей** пары
ключей для подписи обновлений — это не тот сертификат, которого у нас нет
по Р-007, а другая подпись, и закрытый ключ нельзя класть в репозиторий.
Без подписи обновлений механизм работать не должен вовсе: тогда любой,
кто подменит ответ сервера, подменит и приложение.

**Номер версии на виду** — самое дешёвое из четырёх. Версия уже лежит
в четырёх местах и сверяется тестом (`tests/version.test.ts`), так что
показать её — вопрос места: строка состояния, окно параметров или оба.
Значок «есть обновление» рядом с кнопками окна имеет смысл только вместе
с предыдущим пунктом.

### Чего в этапе нет

**Публикации в открытый доступ.** Переносится дальше по решению владельца:
пока в редакторе не хватает вещей, которые чужой человек заметит на первом
часу, показывать его чужим рано.

**Подсказки имён при наборе `[[`.** Граница первого круга говорит
«автодополнение — вне области». Формально это не автодополнение кода, а выбор
из списка файлов проекта, который у нас уже есть в индексе; по существу —
пограничный случай, и решать его владельцу. Записано строкой в «Отложено».

**Живого превью markdown, мини-карты, графа связей** — там же, где были.

### Что решать владельцу по ходу

**Операции с файлами в контекстном меню дерева** — решено в задаче 32:

**Автосохранение.** В Obsidian его не выключить, и привычка не нажимать

расхождение, а не недоделка, — но если за неделю работы рука будет тянуться
к `Ctrl+S` и не находить повода, стоит вернуться к вопросу.

### Что вышло в задаче 32

Меню вебвью снято во всём окне одной строкой на этапе перехвата. Что оно
и правда было, проверено не на слово: с выключенным снятием после правого
щелчка в системе появляется окно класса `Chrome_WidgetWin_1` размером
367×256 — это оно и есть. В снимок `PrintWindow` оно не попадает, потому
что рисуется отдельным окном поверх нашего; так же, как окна ошибок из
задачи 29.

Своё меню сделано тем же `ui/Popup.svelte`, что и меню кодировок: добавлены
второй способ размещения (от точки, вниз и вправо, с переворотом у края),
черта между группами, подпись сочетания и цвет опасности. Расчёт положения
вынесен в `ui/menu-position.ts` и проверяется числами: меню, уехавшее
за нижний край окна, выглядит ровно как не открывшееся.

Набор пунктов — тоже чистый код (`ui/menus.ts`) и тоже под тестом. Тест
среди прочего следит, что каждый пункт ссылается на существующую команду:
пункт, который нажимается и ничего не делает, иначе нашёлся бы только
руками.

Меню рисуется в `AppShell`, а не там, где вызвано: внутри боковой панели
оно уезжало бы вместе с прокруткой и обрезалось бы по краю панели.

Все проверки — в живом окне: меню редактора, вкладки, дерева (файл, папка,
корень, пустое место), поля ввода; перенос курсора к точке щелчка;
переворот у нижнего правого угла; копирование и вставка через пункт меню;
«показать в проводнике». Стенд при этом нашёл на себе два изъяна — оба

### Р-096 · 2026-09-03 · Размер значка — роль, а не одно число

Диагноз к задаче 26, поставленный владельцем: кнопки окна огромные, значки
в боковой полосе крошечные. Причина архитектурная и та же, что была у фонов
до Р-083: слой токенов знает «сколько», но не знает «где».

Размер значка в приложении один — `control-icon-size`, 16 px, — и все места либо
берут его, либо считают от него. Отсюда обе жалобы разом:

* глифы кнопок окна нарисованы в поле `10×10`, как в Windows, а выводятся
  в 16 px — в полтора раза крупнее системных;
* глифы боковой полосы нарисованы в поле `16×16` и выводятся в 16 px внутри
  кнопки 38×38, где референс кладёт 20.

Значит, ролей должно быть несколько: кнопка окна, боковая полоса, строка списка,
крупный знак. Компонент значка размера не назначает — он берёт его из контекста,
как берёт цвет.

Из этого следует и то, что знак в шапке перестаёт быть буквой `Z` на подложке

### Р-105 · 2026-09-03 · Живое представление правится только когда в нём и правда эта вкладка

Дефект, найденный переделкой стенда (задача 30), и он серьёзнее, чем выглядит.

`applyLanguage` заканчивалась так: если вкладка активна и представление есть —
дослать в представление настройку языка и записать получившееся состояние
обратно во вкладку. Условие казалось достаточным. Оно им не было.

У буфера **без языка** — новый файл, `.txt`, незнакомое расширение — ветка
загрузки не содержит ни одного `await`, и вся функция выполняется синхронно,
прямо внутри создания вкладки. В этот момент в представлении лежит ещё
прошлая вкладка. Строка «записать обратно» присваивала новой вкладке чужое
состояние, и её содержимое пропадало до первой отрисовки.

Цена — не косметика. Путь у вкладки при этом остаётся свой, значит сохранение
записало бы в файл текст другого файла. Дефект был в коде с этапа 1 и ни разу
не проявился в ручных проверках: чтобы его увидеть, надо открыть файл без
языка **вторым**, а первый открывается при пустом окне, где представления ещё
нет и ветка другая.

Условие усилено: правим живое представление, только если в нём лежит именно
это состояние. Иначе обновляем состояние вкладки, а до представления оно
доедет обычным путём.

Тест `tests/tab-content.test.ts` держит это место. Его заглушка представления
делает то же, что настоящее, — и это принципиально: первая версия просто
бросала исключение из `dispatch`, тест проходил, ничего не проверив, а причина
терялась в `void`. Заглушка, которая не может повести себя неправильно, делает
бесполезным весь тест.

### Р-104 · 2026-09-03 · Где создаётся заметка — решают те же правила, что и разрешают ссылку

Уточнение к Р-098, найденное при выполнении. Правило «рядом с ссылающейся
заметкой, а при пути в цели — от корня» не выбрано из удобства: это ровно то,
как ссылку разрешает `index/graph.rs`. Косая черта в цели означает путь от
корня, её отсутствие — поиск по имени с выбором ближайшего.

Расхождение здесь было бы худшего сорта: заметка создалась бы не там, где её
потом стала бы искать та же самая ссылка, и `[[Идея]]` показывала бы висячую
ссылку на файл, только что созданный по ней же.

Отсюда и остальные мелочи: расширение `.md` добавляется, только если его нет,
потому что `link_key` снимает ровно `.md` и никакое другое. Обратная косая
черта работает разделителем наравне с прямой — там же и по той же причине.

Что отвергается, а не создаётся:

* цель с `..` — запись мимо папки пользователя недопустима даже по явной
  команде, и путь дополнительно сверяется с корнем;
* имя со знаком, запрещённым в именах файлов Windows, или с управляющим
  знаком — сообщение называет и имя, и знак, потому что ошибка файловой
  системы человеку не скажет ничего;
* цель внутри `.obsidian` — инвариант 2 действует и здесь.

Папки из пути создаются: `[[архив/Старое]]` называет папку сам, и создать её —
часть той же команды, а не самодеятельность.

Пустой файл, а не шаблон. Любая заготовка была бы правкой чужого файла ещё
до того, как его открыли.

### Р-103 · 2026-09-03 · Подпись блока говорит, чем мы его признали

В Obsidian подпись языка нужна потому, что там оформляется режим чтения:
ограждение из обратных кавычек спрятано, и подпись — единственный способ
узнать, какой это язык. У нас редактор исходного текста, ограждение видно
всегда, и подпись, повторяющая написанное в нём, была бы пустой строкой
на экране.

Поэтому подпись показывает не то, что написано в ограждении, а то, чем мы это
признали: ```c++ подписан «C / C++», ```ps1 — «PowerShell». Признание идёт тем
же способом, каким его делает сам разбор markdown, иначе подпись рассказывала
бы про один язык, а подсветка приезжала бы от другого.

Главное же — случай, когда признать не удалось: ```jsonc подписан «нет
подсветки» цветом предупреждения. Из самого текста этого не видно никак; блок
просто остаётся серым, и человек думает на редактор, а не на своё написание.

Ограждение без языка не подписывается вовсе: там никто ничего и не обещал.
Кнопка копирования при этом есть — копировать содержимое надо и оттуда.

Подпись и кнопка стоят на строке ограждения, а не в углу блока, как в Obsidian.
У нас есть горизонтальная прокрутка, и угол уехал бы вместе с текстом.

### Р-101 · 2026-09-03 · Столбец считается в единицах UTF-16, а не в символах

Позиция в строке берётся вычитанием: `head − line.from + 1`. Это постоянное
время, но считает единицы UTF-16, а не настоящие символы. Разница видна только
на строках с астральными знаками — эмодзи и подобным: буква любого алфавита,
включая кириллицу, занимает одну единицу.

Честный подсчёт означал бы просмотр начала строки на каждое нажатие. В обычном
тексте это ничто, но редактор такого класса открывают в том числе на
минифицированном файле в одну строку на несколько мегабайт, и там просмотр
пришёлся бы ровно на путь ввода — то есть на инвариант 6. Постоянное время
важнее точности в случае, где и само понятие «символ» неоднозначно: цепочку
из буквы и модификатора пользователь считает одним знаком, а Unicode — двумя.

Табуляция считается за один столбец, как в Notepad++ по умолчанию: столбец
здесь — позиция в строке, а не координата на экране.

### Р-102 · 2026-09-03 · Стенд инварианта 6 не касался строки состояния

Найдено при подготовке задачи 27. Замер печатает в собственный `EditorView`
с минимальным набором расширений — своя разметка, свой документ, никакой связи
с состоянием вкладки. Значит, строка состояния при этом не перерисовывается,
и вся её работа в измерение не попадала.

Это делает недействительным вывод из приёмки этапа 3, где счётчик курсоров
объявлен неизмеримо дешёвым: числа были верные, но получены на пути, в котором
счётчика не было. Проверка, которая не может провалиться, выглядит точно так же,
как проверка, которая проходит, — и здесь она выглядела именно так.

Что сделано сейчас: в стенд добавлена колонка «позиция курсора» — та самая
работа, которую строка состояния делает на каждое изменение, на том же
документе в мегабайт и в тех же двух режимах. Она меряет саму работу.

Первый прогон показал ноль и тем напомнил, зачем всё это: одно чтение короче
разрешения таймера, и ноль означал не «бесплатно», а «не измерено». Считается
среднее по пяти тысячам чтений, в микросекундах. Вышло **0,06 мкс** и в покое,
и под индексацией — против 3,3 мс на саму правку. То есть цена действительно
пренебрежимая, но теперь это измеренное число, а не предположение.

Чего не сделано было тогда: путь через реактивность и отрисовку кадра.
Владелец включил переделку в этап 4 — задача 30, и она сделана.

**Что вышло.** Стенд печатает в настоящую вкладку; первой строкой оставлен
прежний путь, мимо приложения, — как база для сравнения. Цена собственной
обвязки видна прямо: 3,3 мс против 3,7 мс, то есть около 0,4 мс на всё вместе —
обновление вкладки, счётчик курсоров, позицию курсора, отложенный черновик
и перерисовку. Под индексацией 3,9 мс при худшей 5,8.

Колонка «позиция курсора» из задачи 27 при этом убрана: она была временной
мерой ровно до этой переделки, а теперь измеряется не по частям, а целиком.

**И главное, ради чего это стоило делать.** Переделка сразу нашла дефект,
который ручные проверки не находили с этапа 1: вкладка с файлом без языка
получала состояние прошлой вкладки, а сохранение записало бы в файл чужой
текст. Разбор — Р-105. Замер, проходящий тем же путём, что и пользователь,
находит то, чего замер рядом с этим путём не найдёт никогда.

### Р-100 · 2026-09-03 · Роль размера задаётся контекстом, а не свойством значка

Р-096 требовал сделать размер значка ролью. Способов было два: свойство
у компонента (`<Icon size="tile" />`) или наследование, как у цвета.

Выбрано наследование. Значок читает `--zn-control-icon-size`, умолчание —
строка списка, а контекст с другой ролью переопределяет эту переменную у себя
одной строкой:

```css
.button { --zn-control-icon-size: var(--zn-control-icon-size-window); }
```

Почему не свойство: со свойством размер назначается в каждой точке вызова,
и точек этих тридцать четыре. Забыть его в одной — обычное дело, а увидеть
пропуск можно только глазами и только на той теме и плотности, где смотришь.
С наследованием размер назначается там же, где живёт роль, — в контейнере,
которых пять. Новый значок, положенный в кнопку окна или в плитку, окажется
нужного размера сам, и это свойство конструкции, а не дисциплины.

Ролей вышло пять, а не четыре, как предполагал Р-096. Аудит нашёл, что
значок в карточке параметров лежит в такой же квадратной плитке, что и кнопка
боковой полосы, и страдает тем же. Поэтому роль названа по форме — «плитка», —
а не по месту: мест оказалось два.

Заодно закрыт пробел в проверке токенов. Она ловила литералы, но не заметила
бы `var(--zn-опечатка)`: такое значение молча пустое, свойство отбрасывается,
и элемент едет на умолчании браузера. Теперь тест сверяет каждую ссылку
и каждое объявление `--zn-*` со слоем токенов — и заодно следит, что компонент
не заводит под видом токена собственную переменную.

### Р-099 · 2026-09-03 · Знак приложения — единственная двухцветная иконка

Реестр значков держался на правиле «цвет только `currentColor`»: иконка,

### Р-098 · 2026-09-03 · Заметка по висячей ссылке создаётся рядом с ссылающейся

Задача 29 пишет файл в папку пользователя, а Р-049 запрещает делать это без

- **`⎇ main` в строке состояния** — это git-интеграция, её не планировали.
- **«Синхронизировано N мин назад»** — синхронизация вне первого круга.
- **Мини-карта и живое превью markdown** — функции, не оформление;
